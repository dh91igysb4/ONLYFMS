# 지갑과 골드 지급 (펨타듀 밸리 1단계) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 사이트 공용 골드 지갑을 만들고(낚시 골드를 그대로 옮김), 새로 생기는 골드를 사람마다 하루 소프트 상한으로 묶고, 자유 플레이 미니게임이 점수에 비례해 골드를 주게 한다. 이 계획은 설계 §11의 1단계(지갑 핵심 + 사이트 하루 상한 + 낚시 골드 이전)와 2단계(자유 플레이 지급)를 Task로 나누고, 3~5단계는 개요만 둔다.

**Architecture:** DB에 `wallets`(잔액)와 `gold_ledger`(장부, `unique (user_id, reason, ref)`, 줄기 전 금액 `raw_delta`)를 두고, 골드는 `_gold_move` 하나로만 바꾼다. `_gold_move`가 지갑을 잠근 뒤 오늘(KST) 수입 합계를 보고 사이트 하루 상한(`REF × 1.5`, 넘은 몫 20%)을 적용한다(설계 §5.6). 상수 원본은 `src/games/economy.ts`, SQL 사본은 `_economy()`. 지속형 게임은 `WorldLogic` 계약을 넓혀 `ctx.gold`(잔액)를 받고 `gold`(증감)를 돌려주며, `world` 핸들러가 세이브 → 지갑 순서로 잠근 한 트랜잭션에서 장부에 반영한다. 옛 낚시 세이브의 골드는 처음 접속 때 `legacyGold`로 한 번 옮긴다(`logic.version` 현재 + 1). 자유 플레이는 `free_plays` `after insert` 트리거가 `game_modes`의 게임별 수치로 지급하고, 지갑을 잠근 뒤 오늘(KST) 합계로 하루 상한을 지킨다. 화면은 `src/lib/walletStore.ts`(구독 모듈)를 헤더 배지가 보여 주고, `world` 응답 최상위 `gold`와 `my_wallet()`이 채운다.

**Tech Stack:** TypeScript, React 18, Supabase(Postgres·RLS·plpgsql), Deno(`world` 함수 테스트), vitest, pgTAP. 새 의존성 없음.

**Spec:** `docs/superpowers/specs/2026-11-23-wallet-design.md` (승인됨 2026-11-24, 같은 날 인플레이션 억제 개정. §4 REF·목표 속도, §5 지갑, §5.6 사이트 하루 상한, §6 world, §7 자유 플레이, §11 단계, §14 판단)

## Global Constraints

- **착수 조건**: 낚시 확장 2~6단계가 main에 머지된 뒤. 시작할 때 main에서 새 브랜치를 따고 `src/games/fishing/logic.ts`의 `logic.version`을 확인한다. 이 계획에서 `V`는 그 값(지금 7, 4단계 뒤 8 예상), 지갑 변경은 `V + 1`. 문서·커밋에도 실제 숫자를 적는다.
- 착수 시점 `logic.ts`에서 `state.gold`를 쓰는 **모든** 행동을 바꾼다 (`sell`·`buyRod`·`buyBag`·`buyTackle`·`unlockArea`·`teleport`와 그 사이 더해진 것). `State`에서 `gold`를 빼면 `npm run typecheck`가 남은 곳을 잡는다.
- 플랫폼 코드에 게임 id 분기 금지. 게임마다 다른 수치는 manifest(`gold`)와 `game_modes`로.
- DB 변경은 `npx supabase@2 migration new <이름>`으로 만든 새 파일로만. 함수는 `security definer set search_path = public`, `revoke execute … from public, anon, authenticated` 뒤 필요한 역할에만 `grant`. 오류는 `errcode 'P0001'` + 메시지 코드.
- 잠금 순서: 세이브·대국·대회 행 먼저, 지갑 나중. 여러 지갑은 `user_id` 오름차순.
- 골드는 정수(`bigint`), 소수는 내림. 금액 표기 `1,234 G`(`toLocaleString('ko-KR')`).
- `logic.ts`·`economy.ts`는 순수 모듈, 상대 import에 `.ts`. 화면 문구 한국어, 모바일 우선, 색은 `theme.css` 토큰만.

## Review Focus

1. **낚시 골드 이전이 정확히 한 번**: 옛 버전(≤ `V`) 세이브의 `gold`가 첫 `load`/`act` 때 지갑으로 한 번만 들어간다. 같은 사람이 동시에 두 탭에서 열어도, 첫 요청의 `apply`가 오류여도, 다시 열어도 두 번 들어가지 않고 사라지지도 않는다. 이전 뒤 세이브에는 `gold`가 없다. → Task 1, Task 3, Task 4
2. **잔액 음수 불가와 중복 무시**: `_gold_move`가 음수 결과를 `not_enough_gold`로 거절하고 아무것도 바꾸지 않는다. 같은 `(user, reason, ref)`는 두 번째부터 무시된다. world `act`가 잔액보다 큰 지출을 돌려주면 세이브·지갑·장부 모두 그대로이고 400. → Task 1, Task 3
3. **자유 플레이 하루 상한**: 판당 상한, 게임별 하루 상한(오늘 KST), 동시에 들어온 여러 판도 상한을 넘지 않는다(지갑을 잠근 뒤 합계). 숨김 게임·`free = false`·설정 없는 게임은 0. 같은 `client_id` 재전송은 지급 없음. → Task 8, Task 9
4. **플랫폼에 게임 분기 없음**: `world` 핸들러, 트리거, `LocalRunner`, 헤더는 게임 id를 모른다. 차이는 `WorldLogic`(`legacyGold`, `gold`)과 manifest `gold` / `game_modes`가 푼다. `registry.test.ts`가 manifest `gold`와 마이그레이션 값을 비교한다. → Task 2, Task 3, Task 8, Task 10
5. **배포 사이 호환**: DB만 올라간 상태(옛 `world`), 새 `world` + 옛 화면, 새 화면 모두에서 낚시가 동작하고 골드가 사라지지 않는다. 옛 화면은 `view.gold`만 읽고, 새 `world`의 `view.gold`는 지갑 잔액이다. → Task 3, Task 4, Task 7
6. **사이트 하루 상한**: `world`(+)·`free`는 세고 줄이며, `daily_prize`는 세되 줄이지 않고, `migrate`·`admin`·`duel_*`·`contest_*`는 세지도 줄이지도 않는다. 지출(−)은 합계를 줄이지 않는다. KST 자정 경계. 상한은 `_gold_move` 한 곳에만 있다(트리거·핸들러에 상한 계산 없음). `economy.ts`와 `_economy()`가 같다. → Task 1, Task 1b, Task 3, Task 9

  ```sql
    user_id uuid primary key references public.profiles(id) on delete cascade,

    updated_at timestamptz not null default now());
  create table public.gold_ledger (
    id bigint generated always as identity primary key,
    user_id uuid not null references public.profiles(id) on delete cascade,
    delta bigint not null check (delta <> 0),
    balance_after bigint not null check (balance_after >= 0),
    reason text not null check (reason in ('migrate','world','free','daily_prize','duel_stake','duel_payout',

    check (raw_delta is null or raw_delta > delta));
  create index gold_ledger_free_idx on public.gold_ledger (user_id, reason, game_id, created_at);
  create index gold_ledger_day_idx on public.gold_ledger (user_id, created_at);
  create index gold_ledger_recent_idx on public.gold_ledger (created_at desc);

  _wallet_lock(p_user uuid) returns bigint                          -- 없으면 0으로 만들고 for update, 잔액
  _gold_move(p_user uuid, p_delta bigint, p_reason text, p_ref text,
             p_game text default null, p_note text default null) returns bigint
     -- delta 0 → 잔액만; 같은 (user,reason,ref) 있음 → 잔액만; 음수 결과 → P0001 not_enough_gold
     -- delta > 0이고 reason in ('world','free'): 잠근 뒤 s = 오늘(KST) reason in ('world','free','daily_prize')
     --   이고 delta > 0인 줄의 delta 합계; room = greatest(cap − s, 0);
     --   got = least(d, room) + floor((d − least(d, room)) × rate); got < d면 delta = got, raw_delta = d; got = 0이면 장부 없음
     -- reason 'daily_prize'는 줄이지 않음(합계에만 듦). 그 밖의 reason은 상한과 무관. cap·rate는 _economy()에서 읽는다
  my_wallet() returns jsonb          -- {"balance": n, "today": {"<game_id>": n}, "earned_today": n}
     -- today = 오늘(KST) 'free' 게임별 coalesce(raw_delta, delta) 합계, earned_today = 위 s(실제 들어간 수입 합계)
  user_wallet(p_handle text) returns bigint   -- 승인된 대상 아니면 null, 지갑 없으면 0 (user_records와 같은 handle 정규화)
  admin_gold_adjust(p_handle text, p_delta bigint, p_note text) returns bigint
     -- 관리자만(forbidden), 대상 없음 not_found, 메모 1~100자 아니면 note_invalid, reason 'admin', ref gen_random_uuid()
  admin_gold_ledger(p_limit int default 50)
     returns table (id bigint, handle citext, delta bigint, balance_after bigint, reason text, ref text,
                    game_id text, note text, raw_delta bigint, created_at timestamptz)   -- 관리자만, limit은 1~200으로 자름, 최신순
  ```

## 3단계 PR: 정산과 데일리 상금 (`feat/wallet-daily`)

## 4단계 PR: 대전 판돈 (`feat/wallet-duel`)

**Goal:** 1대1 대전에 판돈(0 ~ `STAKE_MAX` 41,000)을 걸 수 있다. 둘이 같은 금액을 맡기고 승자가 모두 가진다. 무승부·무효(대기 만료·취소·첫 행동 전 종료·버전 변경)는 맡긴 만큼 돌려준다.

**Architecture:** `duel_matches.stake`. 맡기기는 `duel` 함수가 대국 행을 잡은 트랜잭션에서 `_gold_move(…, -stake, 'duel_stake', 대국 id, 게임 id)`(만들 때 만든 사람, 참가 때 참가자). 지급·환불은 **`duel_matches` after update 트리거 하나**(`_duel_settle_stakes`)가 `status`가 `finished`/`void`로 바뀌는 순간 장부의 `duel_stake` 줄을 보고 한다. 대국을 끝내거나 무효로 만드는 길(`save()`, `create`의 오래된 대기 일괄 update, `expireIfStale`, 버전 변경 무효)이 여럿이라 한 곳에 모은다.

**Spec:** 설계 §9, §14("랭크·친선 모두 판돈", "트리거 한 곳", "`stake_mismatch`", "첫 행동 전 종료 = 무효 = 환불").

### 4단계 Global Constraints
- 판돈은 정수 0 ~ 41,000. 숨김 게임은 0만(`invalid_stake`). 같은 화면 2인 모드(`/duel/local`)는 판돈 없음.
- 참가 요청은 화면이 본 `stake`를 함께 보낸다. 없으면 0으로 본다(옛 화면). 대국의 판돈과 다르면 409 `stake_mismatch`(`{ stake: 지금 판돈 }`).
- 잠금 순서: 대국 행(`for update`) → 지갑. 트리거는 대국 행 update 안에서 돌므로 이미 대국 행을 잡고 있다. 트리거의 지급은 `user_id` 오름차순.
- 트리거는 `old.status not in ('finished','void') and new.status in ('finished','void')`일 때만 일한다. 금액은 장부 `duel_stake` 줄(실제로 빠진 돈)에서 읽는다 — `stake` 열을 믿지 않는다(맡기기 전에 무효가 되면 돌려줄 것도 없다).
- `not_enough_gold`(postgres 오류)는 `duel` 핸들러에서 트랜잭션 전체를 되돌리고 409 `not_enough_gold`.
- Elo·전적은 판돈과 무관(지금 그대로).
- 배포 순서: DB → `duel` 함수 → Vercel. DB만 먼저: `stake` 기본 0이라 옛 함수 그대로. 새 함수 + 옛 화면: 옛 화면은 판돈을 보내지 않아 0으로만 만들고, 판돈 > 0 대국에 링크로 들어오면 `stake_mismatch` → 새로고침 안내.

### 4단계 Review Focus
1. **돈이 사라지거나 생기지 않는다**: 대국 하나의 `duel_stake` 합 = `duel_payout` 또는 `duel_refund` 합. 모든 무효 경로(대기 10분 만료 두 가지, 취소, 첫 행동 전 종료, 버전 변경, 만든 사람 삭제·설정 불일치)에서 환불. → Task 19, Task 20
2. **동시 참가**: 두 사람이 동시에 참가해도 한 사람만 돈이 빠진다(대국 행 잠금 뒤 상태 확인 → 맡기기). 잔액이 모자란 참가는 대국을 그대로 `waiting`으로 남긴다. → Task 20
3. **`stake_mismatch`**: 만든 뒤 판돈은 바뀌지 않지만, 옛 화면·잘못된 요청이 다른 금액으로 참가하지 못한다. → Task 20
4. **숨김 게임 0만, 상한 41,000**: DB check와 함수 검사 둘 다. → Task 19, Task 20
5. **플랫폼 분기 없음**: 판돈 입력·표시는 manifest `hidden`과 대국 행으로만. → Task 21

## 5단계 PR: 대회 참가비 (`feat/wallet-contest`)

**Goal:** 공식·친선 대회에 만들 때 정한 참가비(0 ~ `FEE_MAX` 41,000)를 둔다. 모인 돈은 끝난 뒤 60/30/10으로 나누고(순위 2명 이하면 1등 독식, 0명이면 전원 환불), 취소하면 전원 환불. 서버는 보태지 않는다.

**Architecture:** `contests.entry_fee`(데일리는 0 제약). `create_contest`(만든 사람 자동 참가 = 그때 차감), `join_contest`·`join_by_invite_code`(대회 행 `for update` 뒤 처음 참가일 때만 차감), `cancel_contest`(장부 `contest_fee` 줄 기준 환불). 분배는 3단계의 `_contest_payouts`에 공식·친선 경우를 더하면 `settle_due`가 그대로 지급한다(취소 대회는 정산 때 남은 환불을 확인).

**Spec:** 설계 §10, §14("참가비는 만든 뒤 바꿀 수 없다", "60/30/10, 2명 이하 독식, 0명 환불").

### 5단계 Global Constraints
- 참가비는 정수 0 ~ 41,000, 만든 뒤 바꿀 수 없다(`update_contest`는 그대로). 숨김 게임이 하나라도 든 대회는 0만(`fee_not_allowed`).
