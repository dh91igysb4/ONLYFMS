# 네온 라이더 (`neon-rider`) 설계

작성: 2026-11-23. 플랫폼 설계(`2026-10-31-onlyfms-platform-design.md`)와 볼 런 설계(`2026-11-07-ball-run-design.md`)의 구조를 따른다. 1~2장은 사용자와 대화로 확정했고, 3장 이후는 사용자가 방법을 맡겨 이 문서에서 정했다("내 판단"으로 표시).

## 1. 의도

Ketchapp의 Rider 무한 모드를 친구들과 최고 점수로 겨루고 싶다. 기준은 하나다: **원작과 최대한 비슷한 손맛.** 한 손가락으로 가속과 공중 회전을 하고, 착지 각도에 따라 살거나 터지는 그 느낌이 나와야 한다.

**어느 시절의 Rider인가:** 2017~2018년 무렵의 예전 버전이다. 보라색 배경에 분홍 네온 길, 점수와 최고 점수만 있는 단순한 게임이던 때의 감성을 만든다. 최신 버전에 붙은 이벤트·업적·꾸미기 아이템은 대상이 아니다. 사용자가 준 녹화가 바로 그 예전 버전이므로 **모습과 손맛의 기준은 녹화**다. 나무위키 문서(사용자가 PDF로 줌)는 최신 버전을 설명하므로 규칙을 확인하는 데만 쓰고, 녹화와 어긋나면 녹화를 따른다.

참고 자료: 사용자가 준 녹화(스트리머 편집 영상, 6분 24초, 게임 화면은 왼쪽 약 800×1080 영역). 영상과 그 프레임은 남의 저작물이므로 저장소에 넣지 않는다. 이 문서에는 거기서 잰 수치만 적는다. 작업 세션에서는 사용자가 올린 파일(`2시간동안_게임만했더니___.mp4`)로 받는다. 구현하는 세션에 파일이 없으면 사용자에게 다시 올려 달라고 한다.

## 2. 목표·비목표·실패 조건

**목표**
- 원작 무한 모드의 조작·물리·장애물 구성·점수 규칙을 재현한다.
- 자유 플레이 전용 점수 게임. 리더보드는 최고 점수만(볼 런과 같은 표시).
- 휴대폰에서 60Hz로 끊기지 않는다.

**비목표** (이번에 만들지 않는다)
- 원작의 레벨 모드, 챌린지, 차량 수집, 테마 해금, 부활
- 최신 버전의 이벤트(4인 경쟁), 업적, 꾸미기(바퀴·트레일·랜딩·폭발)
- 보석의 저장·사용(뽑기). 보석은 판 안에서 줍는 것까지만 만든다(§6)
- 데일리·대회·1대1
- 효과음, 리플레이 화면
- 서버의 점수 재검증(신뢰 모델은 볼 런·양치와 같다. §4.2)
- 움직이는 구조물(녹화의 노란 회전 막대 등). 2단계로 미룬다(§9)

**실패 조건** (동작해도 실패로 본다)
- 차가 궤도에 붙어 가거나 회전이 연출로만 보인다. 착지 각도가 결과를 바꾸지 않는다.
- 생성된 코스에 통과할 수 없는 구간이 나온다.
- 화면에 보이는 상태와 판정이 어긋난다(닿지 않았는데 죽거나, 닿았는데 산다).
- 원작의 이름·로고·차량 그림을 그대로 쓴다.

## 3. 만드는 방법 (세 가지를 비교해 1번으로 정함)

| 방법 | 내용 | 버린/고른 이유 |
|---|---|---|
| **1. 정수 강체 시뮬을 직접 작성 (선택)** | 고정 틱, 정수 연산만. 바퀴 2개 + 차체, 지형은 선분 목록 | `logic.ts`는 외부 의존 없는 순수 함수여야 하고 Edge Function(Deno)이 등록부를 통해 함께 불러온다(CLAUDE.md). 시드+입력 기록(`free_play_logs`)으로 판을 그대로 재현할 수 있다. 손맛 튜닝에 시간이 가장 많이 든다 |
| 2. 물리 라이브러리(planck.js 등) | 강체 거동이 처음부터 그럴듯함 | `logic.ts`에 npm 의존을 넣을 수 없다. 부동소수·삼각함수라 엔진마다 결과가 달라 기록 재현이 깨진다 |
| 3. 가짜 물리 | 차를 궤도에 붙이고 회전만 연출 | 실패 조건 첫 줄에 해당한다 |

사용자는 방법을 맡겼고, 1번으로 간다고 알렸다.

정정: 대화 중에 "서버가 입력을 재생해 점수를 검증한다"고 말했는데 틀렸다. 자유 플레이 점수는 브라우저가 계산해 저장하고, 기록은 재현·분석용이다(볼 런 설계 §1). 1번을 고르는 이유는 위 표의 것이고, 점수 조작 방지는 어느 방법으로도 얻지 못한다.

## 4. 구조

### 4.1 파일 — `src/games/neon-rider/`

| 파일 | 역할 |
|---|---|
| `manifest.ts` | §4.3 |

| `pieces.ts` | 장애물 템플릿(직선·호 기본 도형의 목록)과 선분 변환 |
| `course.ts` | 시드 → 템플릿 이어붙이기, 구간·선분 조회 |
| `sim.ts` | `initSim()`, `step(state, hold, course)` |
| `input.ts` | 누름 여부의 런 길이 부호화·복호화·검증 |
| `logic.ts` | `GameLogic` 래퍼 |
| `bots.ts` | 테스트 전용 봇(통과 가능성 검사) |
| `render.ts` | 캔버스 2D 그리기(카메라, 네온 선, 차, 입자, 점수 팝업) |

`render.ts`·`Game.tsx`를 뺀 나머지는 순수 TS, 외부 의존 없음, 상대 import에 `.ts` 명시. 새 npm 의존은 없다.

### 4.2 흐름

볼 런과 같다. `pickPuzzle`은 `{ seed }`만 돌려준다. `Game.tsx`가 로컬에서 같은 `sim.step`으로 매 프레임 진행하고, 입력을 30틱마다(죽는 틱은 즉시) `onAction({ type: 'i', d })`로 보낸다. 끝나면 기존 경로로 `free_plays`(점수), `free_play_logs`(시드·행동)에 저장된다.

## 5. 물리와 판정 (`sim.ts`)

### 5.1 결정성

- 틱 = 1/60초. 길이 단위 1/16 mm(차 길이 약 2 m = 32000), 각도 단위 1/4096 바퀴.
- 시뮬 상태는 모두 정수. 연산은 `+ - *`, `Math.floor(a / b)`, 비교, `trig.ts`의 표 조회와 정수 제곱근만. `Math.sin/cos/sqrt/atan2/pow` 금지. 중간값은 2^50 미만.
- 같은 시드와 입력이면 어느 엔진에서도 같은 결과.

### 5.2 차 모델 (내 판단)

질점 두 개(뒷바퀴, 앞바퀴)를 길이가 고정된 막대로 이은 위치 기반(Verlet) 모델.

- 각 바퀴는 반지름 `WHEEL_R`의 원으로 지형 선분과 충돌한다(겹치면 법선 방향으로 밀어내고, 법선 속도에 반발 계수 `RESTITUTION`, 접선 속도에 `FRICTION` 적용).
- 막대 길이 제약을 틱마다 `CONSTRAINT_ITERS`회 푼다.
- 차체의 방향과 회전은 두 바퀴 위치에서 나온다. 따로 각도 상태를 두지 않는다. 그래서 한쪽 바퀴만 먼저 닿으면 차가 실제로 튕기고 돈다.
- 이 모델을 고른 이유: 회전·튕김이 연출 없이 물리에서 나오고, 정수로 구현할 연산이 제곱근 하나뿐이다. 관성 모멘트·충격량을 다루는 완전한 강체보다 훨씬 작다.

### 5.3 입력의 효과

입력은 틱마다 누름 여부 1비트.

- **누름 + 뒷바퀴 접지**: 뒷바퀴에 지면 접선 방향으로 `DRIVE_ACC` 가속, 속도 `V_MAX`까지. 이때 앞바퀴가 들리는 반작용(`WHEELIE_ACC`)도 준다. 원작은 땅에서 누르고 있어도 앞이 들려 뒤집힐 수 있고, 그게 죽는 주된 이유 중 하나다(나무위키 개요). 세기는 녹화에 맞춘다.
- **누름 + 두 바퀴 모두 공중**: 두 바퀴에 반대 방향 접선 가속 `SPIN_ACC`를 줘서 뒤로 도는(앞이 들리는) 회전을 만든다. 각속도 `SPIN_MAX`까지.
- **뗌**: 구동·회전 가속 없음. 접지 중엔 `ROLL_DRAG`로 서서히 감속. 공중 각속도는 `AIR_SPIN_DAMP`로 줄어든다(원작에서 손을 떼면 회전이 멈추는 것).
- 중력 `G`는 항상 적용.
- 부스터 구간(바닥의 `»»»`)을 지나면 누르든 안 누르든 진행 방향 속도가 `BOOST_V` 이상이 되게 올린다.

### 5.4 사망

- `crash`: 차체 판정점(두 바퀴 중점에서 차 윗방향으로 `HEAD_OFFSET`만큼 올린 점, 반지름 `HEAD_R`)이 지형에 닿음. 뒤집혀 착지하면 여기에 걸린다.
- `fall`: 차 중심이 현재 구간 최저점보다 `FALL_DEPTH` 아래.
- `give_up`: 플랫폼 행동.
- 죽은 뒤의 `step`은 상태를 바꾸지 않는다.

### 5.5 지형과 충돌 범위

- 지형은 순서가 있는 선분 목록이다. 선분마다 진행 번호가 있다.
- 충돌은 차의 현재 진행 번호 앞뒤 `COLLIDE_WINDOW` 안의 선분과만 검사한다. 루프처럼 화면에서 겹치는 길을, 들어갈 때의 선분에 다시 부딪히지 않고 지나가게 하려는 것이다(내 판단).
- 진행 번호는 바퀴가 마지막으로 닿은 선분의 번호다. 차가 뒤로 굴러가면 번호도 함께 내려간다(쿼터파이프나 루프에서 실패해 되굴러와도 바닥을 뚫지 않는다). 공중에서는 바뀌지 않는다.
- 멈춰 있거나 끼어도 죽지 않는다. 점수는 구간을 지나야만 오르므로 가만히 있어서 얻는 것이 없고, 플레이어는 포기(`give_up`)로 끝낼 수 있다(내 판단).
- 한 번의 적분 단계에서 최대 이동 거리(`V_MAX`와 부스터, 낙하 속도 상한 `V_TERMINAL` 포함)는 `WHEEL_R`보다 작게 유지해 선분을 뚫고 지나가지 않게 한다. 녹화의 속도가 이 한도를 넘으면 한 틱을 여러 단계로 나눠 적분한다. 이 조건을 상수 테스트로 고정한다.

### 5.6 점수

- 장애물 구간 하나를 지날 때마다 +1(차 중심이 구간 끝을 넘는 틱).
- 공중제비: 두 바퀴가 모두 뜬 동안 누적 회전각을 센다. 착지해 죽지 않으면 완전한 바퀴 수만큼 +1씩. 죽으면 0.
- 공중 구간의 정의: 두 바퀴가 모두 뜬 틱에 시작하고, 어느 바퀴든 처음 닿는 틱에 끝난다. 회전각은 부호 있는 순 각도로 누적하고(지형 때문에 앞으로 돈 만큼은 상쇄), 바퀴 수 = floor(|순 각도| / 한 바퀴).
- 지급 시점: 처음 닿은 뒤 두 바퀴가 모두 접지하거나 `LAND_GRACE`틱(초기 12)이 지날 때까지 죽지 않으면 지급한다. 그 사이에 죽으면 지급하지 않는다. 지급 전에 다시 두 바퀴가 뜨면(튕김) 같은 공중 구간으로 이어 센다.
- 퍼펙트 착지(처음 닿는 틱의 차체 각도와 닿은 선분 각도의 차가 `PERFECT_TOL` 이내)면 그 착지의 공중제비 점수 × `PERFECT_MULT`(초기 2).
- `score = min(9999, 구간 점수 + 공중제비 점수)`, `actionCount = tick`.
- 상태에 `lastAward: { tick, flips, perfect }`를 둬서 화면이 "+2" 팝업을 띄운다.

근거: 녹화에서 구간 통과 시 +1, 착지 때 차 옆에 "+1"/"+2"가 떴다가 점수에 합쳐진다("11+2" → 다음 구간 뒤 14). 나무위키 개요가 한 바퀴 +1, 퍼펙트 착지 ×2(5바퀴 퍼펙트 = 10점)를 명시한다. `PERFECT_MULT = 2`로 확정. 앞으로 도는 회전(정회전)도 원작에서 인정되므로 순 각도의 부호와 무관하게 센다(위 정의대로).

착지 때 짧은 감탄 문구를 화면 한쪽에 띄운다(녹화의 "wow!", "right on!" 같은 것). 바퀴 수와 퍼펙트 여부에 따라 고르되 문구는 새로 짓는다. 영어 소문자 한두 단어로 한다. 화면 문구는 한국어라는 저장소 규칙의 예외이고, 예전 감성 때문에 내가 제안하는 것이다(사용자 확인 필요).

### 5.7 초기 수치 (녹화 기준 추정, 구현 첫 작업에서 다시 잰다)

| 항목 | 녹화에서 본 것 | 초기값 |
|---|---|---|
| 화면 대비 차 길이 | 게임 화면 폭의 약 12% | 화면 폭 ≈ 차 길이 × 8 |
| 누르고 있을 때 공중 회전 | 약 0.5초에 반 바퀴 | `SPIN_MAX` ≈ 1바퀴/초 |
| 삼각 장애물 | 밑변 약 차 4대, 높이 약 차 2대 | 템플릿 치수 |
| 차의 화면 위치 | 왼쪽에서 약 25% | 카메라 |
| 중력, 가속, 최고 속도, 반발, 마찰 | 재지 못함 | 구현 첫 작업에서 프레임 단위로 측정 |

구현 계획의 첫 작업은 **녹화 측정**이다: 연속 구간(예: 77~102초, 103~133초)을 60fps로 뽑아 점프 포물선에서 중력을, 평지에서 가속·최고 속도를, 착지에서 반발을 잰다. 길이는 차 길이를 단위로 잰다. 결과를 `constants.ts` 주석에 근거와 함께 적는다.

## 6. 코스 (`pieces.ts`, `course.ts`)

- 템플릿은 `line(dx, dy)`, `arc(반지름, 시작각, 끝각)`, `gap(dx, dy)`(길이 끊김), `boost(길이)`의 목록이다. 호는 `trig.ts` 표로 선분화한다(선분 길이 약 차 길이의 1/8).
- 모든 템플릿은 수평 평지로 시작하고 끝난다. 템플릿 사이에는 길이 `REST_LEN`의 평지를 둔다(녹화에서도 장애물 사이가 평지다).
- 시드에서 sfc32 정수 출력으로 템플릿을 고른다. 원작처럼 점수대에 따라 나오는 구간이 달라지게, 지나온 구간 수에 따라 티어 가중치를 바꾸고(코스는 시드만으로 정해져야 하므로 공중제비 점수는 쓰지 않는다), 최근 3개와 같은 템플릿은 다시 뽑지 않는다. 처음은 고정 평지.
- 첫 세트(녹화에 나온 것, 12개 안팎): 완만한 언덕, 연속 물결, 오르막 끝 점프대, 삼각 스파이크 열(위 삼각 사이에 아래 삼각), 쿼터파이프, 그릇(반원 내리막-오르막), S자 곡선, 루프, 끊어진 호 징검다리(호 사이를 점프), 부스터 직선 + 점프, 계단식 낙하.
- 보석: 템플릿에 노란 점(보석) 위치를 넣을 수 있다. 차가 닿으면 사라지고 입자가 튄다. 그 판에서 주운 개수를 화면 오른쪽 위에 보여 주기만 하고 저장하지 않으며 점수에도 넣지 않는다. 녹화의 화면 구성(그릇 안, 점프 궤적 위의 보석 줄)을 살리려는 것이고 내 제안이다.
- 템플릿·가중치·물리 상수 변경은 `logic.version`을 올린다.

## 7. 화면 (`render.ts`, `Game.tsx`)

- 캔버스 2D. 녹화의 예전 버전 화면을 따른다: 위에서 아래로 어두워지는 보라색 배경, 멀리 보이는 어두운 실루엣 층(느리게 따라 움직임), 분홍 네온 길, 노란 차, 위 가운데의 가늘고 큰 점수 숫자. 지형은 네온 선(넓고 옅은 선 위에 가늘고 밝은 선을 겹쳐 그린다. `shadowBlur`는 휴대폰에서 느려서 쓰지 않는다. 내 판단).
- 차는 새로 그린 단순한 도형(차체 선 + 바퀴 두 개). 원작 차량 그림을 본뜨지 않는다.
- 카메라: 차를 화면 왼쪽 25%, 세로 약 55%에 두고 부드럽게 따라간다. 틱 사이는 보간해 그린다.
- HUD: 위 가운데 큰 점수, 착지 때 차 옆 "+N" 팝업, 사망 시 입자 흩어짐 후 플랫폼의 기존 종료 화면.

## 8. 테스트와 통과 기준

- `sim`: 모든 상태가 정수, 같은 입력이면 같은 결과, 막대 길이 오차 한도, 한 틱 이동 < `WHEEL_R`, 평지 가속·최고 속도, 공중 회전과 뗐을 때 감쇠, 정착지 생존·뒤집힌 착지 사망, 공중제비 수 세기, 퍼펙트 판정.
- `course`: 템플릿 이음(평지 시작·끝), 시드 결정성, 최근 3개 중복 없음.
- `bots`(통과 게이트): 템플릿마다 누름 패턴을 탐색하는 봇이 진입 속도 최저·최고 양쪽에서 통과 패턴을 찾아야 한다. 최저는 템플릿 앞 평지(`REST_LEN`)의 시작점에 정지한 상태, 최고는 `V_MAX`(부스터 직후면 `BOOST_V`)로 그 평지에 들어온 상태다. 따라서 `REST_LEN`은 정지에서 다시 속도를 붙일 만큼 길어야 하고, 더 빠른 속도가 필요한 템플릿은 자체 도움닫기를 포함한다. 못 찾는 템플릿이 있으면 테스트 실패.
- `input`: 부호화 왕복, 잘못된 입력 거부, 묶음 길이 상한.
- `registry.test.ts`·DB 테스트: `scoreMax`와 `score_max` 일치, 9999 저장, 10000 거부.
- `Game.test.tsx`: 마운트, 입력 → `onAction` 묶음, 종료 표시.
- 머지 뒤 수동 확인(바로 공개): 실제 휴대폰에서 녹화와 나란히 놓고 점프 거리·회전 속도·착지 느낌 비교.

## 9. 단계

1. **1단계(이 문서)**: 정적 지형 + 부스터, 바로 공개로 머지(사용자 결정, 저장소의 숨김 우선 절차의 예외) → 사용자가 실제 기기에서 손맛 확인 → 수치 조정. 조정으로 물리가 바뀌면 `logic.version`을 올리고, 그 전 점수를 지울지는 그때 사용자가 정한다.
2. **2단계(별도 설계)**: 움직이는 구조물(회전 막대, 움직이는 발판). 1단계 손맛이 확정된 뒤에 한다. 지형이 움직이면 충돌 계산이 달라지므로 손맛 문제와 섞지 않으려는 것이다(내 판단).

## 10. 만드는 사람에게 맡기는 것

- **모델 수정 권한**: 기준은 1장의 손맛이다. 녹화 측정 결과가 5장의 규칙(뒷바퀴만 구동, 두 바퀴가 다 떴을 때만 회전 등)과 어긋나면 규칙을 녹화에 맞게 고친다. 지켜야 하는 것은 2장의 실패 조건과 5.1의 결정성뿐이다. 고친 내용은 이 문서에 반영한다.

- 정수 고정소수 표현의 세부(보조 누산기, 반올림 방향), 제약 반복 횟수, 상수의 최종 값
- 템플릿 DSL의 구체 문법과 템플릿별 치수
- 봇의 탐색 방식
- 차·입자·배경의 구체 모양(2장·7장 조건 안에서)
- 캐시·메모리 관리
