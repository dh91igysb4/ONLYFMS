# 펨타듀 낚시 — 옷장(캐릭터 꾸미기) 설계 (2026-11-24)

상태: **초안** (사용자 결정 반영, 밤샘 작업 중 작성 — 아침 확인 대기)

앞선 설계: `2026-11-23-fishing-world-design.md`(넓은 세계·도전과제), `2026-11-23-wallet-design.md` §15(집·캐릭터 가격 원칙). 이 문서는 낚시 6단계 마무리(`logic.version` 9) 위에 캐릭터 옷장을 더한다.

## 1. 의도

사이트가 "집과 캐릭터를 키우는" 쪽으로 가고 있다(지갑 설계 §15). 낚시 장비는 한 달이면 다 사지만, 그 뒤에도 골드를 쓸 곳이 있어야 한다. 옷장은 그 첫 골드 쓰는 곳이다. 수입에는 아무 영향이 없고 보기만 바뀐다.

사용자 결정(원문 요약, 구속력 있음):
- 낚시 세계의 캐릭터 **그리고** 프로필 페이지에 보인다.
- 꾸밀 수 있는 곳: 모자, 상의·하의, 머리 모양·색, 손에 든 낚싯대 겉모습(성능은 낚싯대 단계 그대로).
- 얻는 법: 대부분 상점에서 골드로 산다(몇 개는 아주 비싸게). 몇 개는 업적으로만 얻는다(도전과제 깨기, 전설 잡기, 한 지역 도감 완성 등).
- 추가 결정: 아스톤빌라·리버풀·맨유·토트넘·레스터·뉴캐슬 유니폼은 필수. 단 **각 구단의 일반적인 색 배합·무늬만** 쓰는 자체 픽셀 그림이고, 엠블럼·로고·스폰서·제조사 표시·구단 이름은 그림과 화면 어디에도 넣지 않는다. 이름은 색·무늬로 짓는다("클라렛·하늘 유니폼", "흑백 줄무늬 유니폼").

## 2. 목표 / 비목표 / 실패 조건

**목표**
- 부위 6개: 모자(`hat`), 상의(`top`), 하의(`bottom`), 머리 모양(`hair`), 머리 색(`hairColor`), 낚싯대 겉모습(`rodSkin`). 부위마다 하나씩 입는다.
- 품목 73개(부위마다 9~16개, 상의는 유니폼 6벌 때문에 더 많다). 무료 기본 부위마다 2개(낚싯대 겉모습은 1개), 업적 전용 10개.
- 서버 행동 `buyWear`(사면 바로 입는다)·`wear`(가진 것 입기). 서버가 값·소유·업적 조건을 검증한다.
- `logic.version` 10. v9 세이브는 migrate에서 기본 옷차림(지금 캐릭터와 똑같은 모습)이 된다.
- 낚시 장면의 모든 캐릭터 그림(아래·위·옆 3방향 + 왼쪽은 좌우 뒤집기, 대기·걷기 2장·던지기·감기 = 15장)에 옷차림이 겹쳐 그려진다. **기본 옷차림은 지금 그림과 픽셀 하나까지 같다.**
- 옷차림이 바뀔 때 한 번만 15장을 합성해 캐시한다. 매 프레임 합성하지 않는다.
- 프로필 요약 탭에 낚시 캐릭터(앞모습)가 보인다. 플랫폼 코드는 게임 id로 분기하지 않는다(§7).
- 옷장 창(한국어, 모바일 우선, 캔버스 밖은 theme 토큰): 큰 미리보기(4방향 돌려 보기), 부위 탭, 품목 목록(가진 것·살 수 있는 것·업적 조건), 입기·사기.

**비목표**
- 집 꾸미기(3번 작업의 다른 절반), 레벨형 업그레이드, 되팔기(지갑 설계 §15 "되팔기 없음").
- 다른 사람의 낚시 세계에 내 캐릭터가 보이기(멀티플레이 없음).
- 피부색·얼굴·신발 따로 고르기. 신발은 하의에 딸린다.
- 품목별 별도 아이콘 그림. 목록의 그림은 그 품목을 입힌 캐릭터 미리보기(작게)로 대신한다.
- 지갑 연결. 지갑이 들어오기 전에는 낚시 세이브의 `gold`로 산다(§8).

**실패 조건 (동작해도 실패)**
- 옷이 낚시 성능(바·입질·추첨·가격)에 영향을 준다.
- 기본 옷차림 캐릭터가 지금 그림과 달라 보인다(배포만 했는데 모두의 캐릭터가 바뀐다).
- 어떤 방향·자세에서 모자가 머리에서 떨어져 보이거나, 낚싯대·줄 끝(`ROD_TIP`)이 옷에 가려 줄이 허공에서 시작한다.
- 업적 전용 품목을 골드로 살 수 있거나, 조건을 못 채웠는데 입을 수 있다.
- 유니폼에 엠블럼·로고·글자·구단 이름이 있다(그림·이름·설명·`alt` 어디든).
- 옷장을 열 때마다 또는 매 프레임 합성이 돌아 폰에서 끊긴다.
- 프로필 화면 코드에 `'fishing'` 같은 게임 id 분기가 생긴다.

## 4. 그림 합성

### 4.1 원칙
- 새 순수 모듈 `outfit.ts`가 `(포즈 이름, 옷차림) → Sprite`를 만든다. 입력은 지금 `sprites.ts`의 15장 캐릭터 그림이고, 결과도 같은 `Sprite`(글자 = 픽셀) 형식이라 `drawSprite`가 그대로 그린다.
- 그림 자료(색·덧그림)는 `wearArt.ts`(화면 전용). 품목 목록(이름·가격·조건)은 `wardrobe.ts`(서버·화면 공용, 그림 없음) — `world` 함수 번들에 픽셀이 들어가지 않는다.
- 합성 순서(한 장):
  1. **색 바꾸기**: 바람막이 `j/J/z` → 상의 색, 바지 `l/L` → 하의 색, 장화 `b` → 신발 색, 머리 `a/A` → 머리 색, 낚싯대 `r/R/g` → 겉모습 색.
  2. **무늬**: 상의는 `plain`·가로줄(`stripeH`)·세로줄(`stripeV`)·체크(`check`), 소매(`sleeve`: 줄마다 상의 칸의 맨 왼쪽·오른쪽 칸), 가운데 선(`z` 지퍼 칸) 색을 따로 둘 수 있다. 하의는 `plain`·체크·세로줄, 반바지(열마다 맨 아래 바지 칸 → 피부).
  3. **모자 벗기기**(비니 계열이 아닐 때): 비니 칸(`h/H/c`)을 머리색으로 바꾸고 방울(`p`)과 머리 위 칸을 지운 뒤, 새로 머리가 된 칸 위에 외곽선을 다시 긋는다. 이것이 "짧은 머리"다.
  4. **머리 모양 덧그림**: 방향(아래·위·옆)마다 대기 그림 좌표로 그린 덧그림을 그 장의 머리 위치(§4.2)에 맞춰 얹는다. 모자를 쓰면 덧그림의 7번째 줄(머리띠 줄) 위쪽은 그리지 않는다.
  5. **모자 덧그림**: 방향마다 하나. 비니 계열은 원래 그림을 둔다(색만 바꿈).
  6. **낚싯대 다시 칠하기**: 원래 그림의 낚싯대 칸(`r/R/g`)을 맨 위에 다시 칠한다. 줄 끝 좌표(`ROD_TIP`)가 늘 낚싯대 칸이라 줄이 끊기지 않는다.
- 외곽선은 지금 그림과 같은 `#2a2135`.

### 4.2 머리 위치
- 장마다 대기 그림 대비 머리 이동(`dx, dy`)을 표로 둔다: 옆 걷기 0과 위 던지기는 `dy = 1`, 옆 던지기(머리를 젖힌 그림)는 `dx = 1`, 나머지는 0.
- 테스트: 표의 이동만큼 옮긴 대기 그림의 비니 띠(`c`)가 그 장의 비니 띠와 겹친다(옆 던지기는 젖힌 그림이라 겹침 대신 모자 칸이 머리 칸 위에 있는지만 본다).

### 4.3 캐시
- 화면은 `outfitKey(옷차림)`(부위 id를 이은 문자열)마다 15장을 한 번에 합성해 `Map`에 둔다(최근 8개까지). 장면은 옷차림이 같으면 같은 Sprite 객체를 받는다. 테스트가 같은 키에 같은 객체를 돌려주는지 확인한다.
- 옷장 미리보기도 같은 캐시를 쓴다. 품목 목록의 작은 그림은 품목 하나를 입혀 본 앞모습 PNG(`data:` 주소)이고 `(옷차림 키, 배율)`마다 한 번 만든다.

### 4.4 미리보기 점검
- `scripts/preview-wardrobe.ts`(node `--experimental-strip-types`로 실행)가 모든 품목을 기본 옷차림에 하나씩 입혀 4방향 PNG를 `/home/claude/preview/wardrobe/`(인자로 바꿀 수 있음)에 쓴다. 구현 중 눈으로 본다. 테스트·빌드에는 들어가지 않는다.

```ts
type Outfit = { hat: string; top: string; bottom: string; hair: string; hairColor: string; rodSkin: string }
State += {
  /** 산 옷 `부위:id`(영구, 중복 없음. 검정은 바지·머리·낚싯대에 다 있어 부위를 붙인다). 무료·업적 품목은 넣지 않는다 */
  wardrobe: string[]
  /** 입은 옷 */
  outfit: Outfit
}
```
- 가졌는가 `ownsWear(state, id)`: 무료 품목, 또는 `wardrobe`에 있음, 또는 업적 조건을 채움. 업적은 저장하지 않고 매번 `challenges`·`legends`·`dex`로 계산한다(모두 되돌아가지 않는 값이라 한 번 얻으면 계속 가진다).
- 업적 조건 종류: `{ kind: 'challenge', id }`, `{ kind: 'allChallenges' }`, `{ kind: 'legends', count }`, `{ kind: 'areaDex' }`(어느 한 지역이라도 그 지역 어종을 모두 도감에).

### 5.2 행동
- `{ type: 'buyWear', slot, id }`: 상점 품목(가격 > 0, 업적 아님)만. 이미 가졌으면 `already_owned`, 업적 품목이면 `not_for_sale`, 모르는 id `bad_wear`, 골드 부족 `not_enough_gold`. 성공하면 골드를 빼고 `wardrobe`에 넣고 **그 부위에 바로 입힌다**.
- `{ type: 'wear', slot, id }`: 부위가 맞고 가진 품목만. 모르는 부위·id `bad_wear`, 부위가 다르면 `bad_wear`, 안 가졌으면 `not_owned`.
- 둘 다 낚시 중(`pending`)에도 된다(성능 영향 없음). 화면은 낚시 중 메뉴를 잠그므로 실제로는 대기 중에만 누른다.
- 상점 위치는 서버가 보지 않는다(지금 상점 구매와 같음, 세계 설계 §8.4).

### 5.3 migrate
- v9 이하: `wardrobe = []`, `outfit = 기본`(비니·바람막이·남색 바지·짧은 머리·갈색·대나무).
- v10: `wardrobe`는 알려진 상점 품목 키(`부위:id`)만 중복 없이. `outfit`은 부위마다 그 부위의 알려진 품목이고 가진 것일 때만 남기고, 아니면 그 부위 기본값.

### 5.4 view
- `view`는 지금처럼 `state`에서 `pending`만 바꾼 것이라 `wardrobe`·`outfit`이 그대로 나간다. 업적 소유는 화면이 같은 `ownsWear`로 계산한다(값이 view에 다 있다).

## 6. 가격 근거
- 지갑 설계 §15: 집·캐릭터를 "다 갖춘 느낌"까지 **90일 이상**(`REF × 120` 이상). 옷장은 그 절반쯤인 **`REF` × 65 ≈ 1,340,000 G**(하루 1시간 + 사이트 상한이면 약 45~50일). 나머지는 집 꾸미기(3번 작업)가 채운다.
- 부위마다 사다리: 싼 첫 품목 2,000~6,000 G → 중간 10,000~40,000 G → 비싼 60,000~140,000 G. 유니폼은 중상(28,000~33,000 G).
- 되팔기 없음. 수입 배율 없음. 최고 레벨이 없는 끝없는 골드 쓰는 곳은 집 쪽 레벨형 업그레이드가 맡는다(옷장은 목록이 정해진 큰 골드 쓰는 곳).
- `wardrobe.test.ts`가 상점 총액이 `REF × 55 ~ 75` 안인지, 부위마다 가장 비싼 품목이 가장 싼 품목의 10배 이상인지 고정한다.

## 7. 프로필 표시 (플랫폼, 게임 분기 없음)
- `Manifest.avatar?: { label: string }`: 이 지속형 게임은 프로필에 캐릭터를 보여 준다.
- `WorldLogic.avatar?(state): string`: 캐릭터를 그릴 짧은 문자열(낚시는 옷차림 JSON).
- `world` 함수: 행동(`act`) 뒤 `records`를 쓸 때, `logic.avatar`가 있으면 `game_records`에 키 `avatar`(값 0, `detail` = 문자열)를 함께 upsert한다. **DB 변경 없음**(`game_records`는 키 제한이 없고 `user_records`가 모든 행을 돌려준다).
- 화면 등록: `src/games/ui.ts`의 `getAvatarComponent(id)` → `ComponentType<{ data: string; size: number }>`. 낚시는 `Avatar.tsx`가 앞모습 대기 그림을 캔버스에 그린다(모르는 값은 기본 옷차림).
- 프로필 요약 탭 맨 위 `AvatarSection`: `user_records`에서 `key = 'avatar'`인 행 중 manifest에 `avatar`가 있고 화면이 등록된 게임만 그린다. 없으면 아무것도 그리지 않는다. 기록 탭(`RecordsSection`)은 manifest `records`에 선언된 키만 그리므로 `avatar` 행은 거기 나오지 않는다.
- 등록부 테스트: `avatar` manifest ⇔ `logic.avatar` ⇔ `getAvatarComponent` 셋이 같이 있고, `records` 키에 `avatar`가 없다.
- 배포 직후에는 행이 없다. 낚시에서 행동을 한 번이라도 하면(던지기 등) 생긴다.

## 8. 지갑 이후
- 구매는 지금 다른 낚시 구매처럼 `state.gold`에서 뺀다(`buyWear`의 한 줄). 지갑 2단계에서 낚시 구매가 지갑으로 옮겨갈 때 같은 자리만 바뀐다(지갑 설계의 "낚시 구매" 이전 절차를 그대로 따른다). 옷 소유·입은 옷은 낚시 세이브에 남는다.

## 9. 화면
- 옷장 창(`menu = 'wardrobe'`): 가방 창 위쪽 "옷장" 버튼과 상점 창 "옷 가게" 버튼으로 연다. 아래 줄 메뉴 버튼은 늘리지 않는다(320px에 다섯 개가 한계).
- 창 구성: 위쪽 미리보기(캐릭터 4배, 방향 돌리기 버튼, 고른 품목을 입혀 본 모습) → 부위 탭 6개 → 품목 목록(작은 앞모습 그림·이름·상태: 입는 중 / 보유 / 가격 / 업적 조건).
- 품목을 누르면 미리보기에 입혀 본다. 가진 것이면 "입기", 상점 품목이면 "사기"(상점 문 앞에서만 켜지고, 아니면 "상점에서 살 수 있어요"), 업적 품목은 조건 문구만.
- 캔버스 밖 색은 theme 토큰만. 미리보기 캔버스 안 배경은 캔버스 예외(낚시 캔버스 내부 색).

## 10. 판단 (밤샘 작업 규칙의 Ruling)
- 품목 목록·가격은 §3 — 상점 총액 `REF × 65`로 집과 절반씩 나눈다 — 틀리면 `wardrobe.ts` 숫자만 고친다(세이브 형식 영향 없음).
- 무료 기본은 부위마다 2개(낚싯대 겉모습 1개) — 처음부터 바꿔 볼 수 있게 — 틀리면 가격만 바꾼다.
- 업적 소유는 저장하지 않고 계산한다 — 조건 값이 모두 되돌아가지 않고 migrate가 단순해진다 — 나중에 되돌아갈 수 있는 조건을 넣으면 그때 저장으로 바꾼다.
- 사면 바로 입는다 — 누르는 수를 줄인다 — 원치 않으면 다시 입기 한 번.
- 옷장은 아래 줄이 아니라 가방·상점 창에서 연다 — 320px 아래 줄 다섯 버튼 한계 — 찾기 어렵다는 말이 나오면 가방 버튼 길게 누르기 등으로 바꾼다.
- 프로필 캐릭터는 `game_records`의 `avatar` 키로 — 마이그레이션 없이 기존 RLS·RPC 그대로 — 기록 행 하나가 늘 뿐이다.
- 프로필은 요약 탭 맨 위에 — 처음 들어오면 보이는 곳 — `user_records`를 요약·기록 탭에서 각각 부른다(작은 RPC 하나 더).
- 유니폼 6벌은 색·무늬만, 이름은 색으로 — 사용자 지시(엠블럼·로고·구단 이름 금지) — 이름에 구단 이름이 들어가면 테스트가 실패한다.
- 머리 모양은 업적 전용을 두지 않는다 — 덧그림이 가장 많이 드는 부위라 상점 9개로 둔다 — 나중에 더할 수 있다.
