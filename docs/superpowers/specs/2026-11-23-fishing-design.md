# 낚시 게임 설계 (`fishing`) — 2026-11-23

상태: **승인 대기** (2차 개정: 저장소를 읽고 6절·7절을 실제 구조에 맞춰 고침)

## 1. 의도

onlyfms에 세이브가 있는 성장형 낚시 게임을 넣는다. 친구들이 각자 캐릭터를 키우고(돈 모아 더 좋은 낚싯대 구매, 나중에는 배를 사서 배낚시), 프로필에서 서로의 기록을 업적처럼 비교한다.

기존 게임은 전부 "문제 하나 → 점수"(솔로) 또는 "한 판 대전"(대전)이다. 이 게임은 판 단위가 없는 첫 지속형 게임이라 두 계약 어디에도 맞지 않는다.

## 2. 목표 / 비목표 / 실패 조건

**목표 (1차)**
- 부두 낚시터 1곳에서 캐스팅 → 입질 → 챔 → 바 미니게임 → 가방 → 상점 판매 → 낚싯대 구매의 고리가 돈다.
- 계정별 세이브가 서버에 있고 기기를 바꿔도 이어진다.
- 프로필에 기록 3종이 뜬다: 누적 수익, 최대어, 도감 완성도.

**비목표 (1차에서 안 함)**
- 배, 먼바다, 두 번째 낚시터 (2차. 지역 개념만 데이터 구조에 미리 넣는다)
- 농사, NPC, 계절, 날씨, 시간 흐름
- 미끼, 찌, 통발, 보물상자
- 실시간 동시 플레이
- 미니게임 입력의 서버 재검증
- 데일리·대회·자유 플레이 리더보드 편입 (판 점수가 없다)
- 낚시 전용 순위표

**실패 조건 (동작해도 실패)**
- 콘솔에서 값 하나 바꿔서 골드나 기록을 올릴 수 있다.
- 원작 게임의 스프라이트, 타일, UI 이미지를 그대로 쓰거나 베껴 그렸다.
- 장비를 안 사는 게 기록에 유리하다.
- 모바일 터치로 플레이가 안 된다 (CLAUDE.md: 모바일 우선).
- 플랫폼 코드에 `if (game === 'fishing')` 같은 게임별 분기가 생겼다 (CLAUDE.md 금지 사항).

## 3. 접근 방식

세이브를 누가 책임지느냐로 세 가지를 비교했다.

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 브라우저 저장, 기록만 서버 전송 | 가장 빠름 | 기기 변경 시 소실, 골드 조작 가능 |
| **B** | **서버가 세이브 보유, 값·잔액은 서버 계산** | 기기 간 이어하기, 골드 직접 조작 불가 | 서버 코드·테이블 필요, 미니게임 성공 여부는 신뢰 |
| C | 미니게임 입력까지 서버 재검증 | 조작 거의 불가 | 작업량 2배 이상 |

**B로 결정 (사용자 선택).** A는 프로필 기록이 무의미해지고, C는 친구끼리 쓰는 사이트에 과하다.

참고: 기존 자유 플레이 점수(볼 런 등)는 브라우저가 계산한 점수를 `free_plays`에 직접 넣는다. 즉 B는 지금 플랫폼의 자유 플레이보다 엄격한 수준이다. 누적되는 재화라서 그만한 이유가 있다.

## 4. 게임 규칙

### 4.1 한 번의 낚시
1. **캐스팅**: 누르고 있으면 게이지가 0↔100% 왕복, 떼는 순간 거리 확정. 멀수록 큰 개체 확률이 조금 오른다.
2. **입질 대기**: 서버가 정한 시간(1.5~6초) 뒤 입질 표시. 클라이언트는 입질을 시각으로만 안다. 어종·크기는 아직 모른다.
3. **챔**: 입질 뒤 0.8초 안에 입력하면 클라이언트가 `hook`을 보낸다. 서버는 입질 시각 이후이고 창(0.8초)과 지연 여유(1.5초) 안일 때만 받아, 그때 처음으로 어종·크기를 알려 준다. 놓치면 실패.
4. **바 미니게임**(어종 난이도는 `hook` 응답 기준; 성공은 챈 시각부터 2초 이상 지나야 인정): 세로 트랙에서 물고기 아이콘이 위아래로 움직이고, 플레이어는 누르면 올라가고 떼면 내려가는 바를 조종한다. 물고기가 바 안에 있으면 진행 게이지 상승, 밖이면 하락. 가득 차면 성공, 바닥나면 실패.
5. **퍼펙트**: 물고기가 바 밖으로 한 번도 안 나가면 판매가 1.25배.
6. 성공 시 가방에 들어간다. 가방 20칸, 가득 차면 캐스팅 불가.

### 4.2 어종 (초기 밸런스, 빌더가 조정 가능)

실제 어종 이름을 쓰는 자체 데이터. 1차 부두 12종.

| 등급 | 어종 | 기본가 | 크기(cm) | 난이도 | 필요 낚싯대 |
|---|---|---|---|---|---|
| 흔함 | 멸치, 전갱이, 망둥어, 고등어 | 20~50 | 8~45 | 낮음 | 1단계 |
| 보통 | 숭어, 우럭, 도다리, 오징어 | 80~150 | 20~70 | 중간 | 1단계 |
| 희귀 | 참돔, 농어, 방어 | 300~600 | 40~110 | 높음 | 2단계 |
| 전설 | 다금바리 | 2500 | 80~140 | 매우 높음 | 3단계 |

판매가 = 기본가 × (0.7 + 0.6 × 크기 백분위) × (퍼펙트 ? 1.25 : 1), 정수 반올림.
난이도는 미니게임에서 물고기 이동 속도와 방향 전환 빈도로 반영한다.

### 4.3 낚싯대

| 단계 | 가격 | 효과 |
|---|---|---|
| 1 대나무 | 기본 지급 | 기준 |
| 2 유리섬유 | 1,500 | 바 길이 +15%, 희귀 확률 ↑, 희귀 어종 해금 |
| 3 카본 | 8,000 | 바 길이 +30%, 전설 해금 |
| 4 명장 | 40,000 | 바 길이 +45%, 입질 대기 20% 단축 |

2차의 배(예: 150,000)가 4단계 뒤 목표가 되도록 가격 곡선을 잡았다.

### 4.4 화면
- **낚시터**: 탑다운 고정 화면 하나. 부두 끝에 캐릭터가 서 있고 이동은 없다(1차). 상단 골드, 하단 가방 요약, 버튼(가방 / 상점 / 도감).
- **가방**: 20칸 격자, 물고기별 크기와 예상 판매가.
- **상점**: 전체 판매, 낚싯대 구매 목록.
- **도감**: 어종별 잡은 수와 최대 크기. 미발견은 실루엣.

## 5. 그래픽

전부 자체 제작 픽셀아트. 16px 타일, 정수 배율, `image-rendering: pixelated`. 필요한 것: 캐릭터 3포즈(대기/캐스팅/낚는 중), 부두, 물 타일(2프레임), 어종 12종, 낚싯대 4종, UI 패널.

원작 게임의 이미지는 추출·모사하지 않는다. 사용자 스크린샷은 화면 흐름 참고용으로만 쓴다.

색: 캔버스 내부는 자체 팔레트를 쓴다. CLAUDE.md 금지 사항의 예외 목록(양치 캔버스, 볼 런·몰래 수능 장면)에 "낚시 캔버스 내부 색"을 추가한다. 캔버스 밖 메뉴는 theme.css 토큰만 쓴다.

## 6. 기술 설계

### 6.1 플랫폼에 세 번째 종류 추가: `world`

대전을 넣을 때 `category: 'duel'`과 별도 등록부·라우트를 만든 것과 같은 방식이다.

- `Manifest.category`에 `'world'` 추가. `modes`는 모두 false (대전과 같음).
- `src/games/index.ts`에 `worlds` 등록부와 `getWorld(id)`. 모듈 형태는 `{ manifest, logic }`이고 `logic`은 아래 `WorldLogic`.
- `src/games/ui.ts`에 `getWorldComponent(id)`. 컴포넌트는 props 없이 스스로 서버와 통신한다(지속형은 플랫폼이 쥘 "판 상태"가 없다).
- 라우트 `/world/:game` → `src/platform/world/WorldPage.tsx`. 승인·숨김 확인 뒤 컴포넌트를 그릴 뿐이다.
- `GamesPage`는 지금 솔로 `games`만 나열한다. world 게임 카드도 같은 격자에 뜨게 하고 버튼은 "들어가기"(`/world/:game`) 하나다.
- 마이그레이션: `game_modes ('fishing', false, false, false)` + `hidden_games ('fishing')`. `registry.test.ts`가 `games + duels + worlds`를 비교하도록 고친다.

### 6.2 게임 코드: `src/games/fishing/`

- `manifest.ts`: id `fishing`, 이름 "낚시", `category: 'world'`, `hidden: true`, `records`(6.4).
- `data.ts`: 어종·낚싯대·지역 표. **유일한 원본.** 외부 의존 없음, 상대 import에 `.ts` 명시(Deno 호환).
- `logic.ts`: 순수 함수. `version`, `rollCatch(rng, save, area, power)`(어종·크기·입질 대기 추첨), `price(fish)`, `canBuyRod(save, tier)`, `applyResolve`, `applySell`, `applyBuy`, `records(save, dex)`. 미니게임 물리(`stepBar`)도 여기에 둬서 테스트한다.
- `logic.test.ts`: 테스트 먼저.
- `Game.tsx`: Canvas 2D 렌더링과 입력, 메뉴는 React DOM. 엔진 라이브러리 없음.
- 입력: 누르기 하나(터치/마우스/스페이스)로 캐스팅·챔·바 조종 전부.

### 6.3 서버: Edge Function `supabase/functions/world/`

`play`·`duel`과 같은 방식으로 `src/games/index.ts`를 상대 경로로 import해 `logic.ts`를 그대로 쓴다. 가격·확률 표가 TypeScript 한 곳에만 있게 하려는 것이다(SQL 함수로 짜면 표를 SQL에 한 벌 더 써야 하고 어긋난다).

요청: `POST /world` `{ game, action: 'load' }` 또는 `{ game, action: 'act', payload }`, 사용자 JWT 인증, 승인된 사용자만. 함수는 게임을 모르고 등록부의 `WorldLogic.apply`를 돌린다. 아래 표는 낚시 로직이 받는 payload다.

| action | 하는 일 |
|---|---|
| `load` | 세이브·가방·도감 반환. 없으면 초기 세이브 생성 |
| `cast { area, power }` | 미해결 캐스트 폐기. `rollCatch`로 **서버가 추첨**해 저장하고 입질 대기 시간만 반환(어종·크기는 숨김) |
| `hook` | 입질 시각 ≤ 지금 ≤ 입질 + 0.8초 + 1.5초일 때만. 처음 성공하면 `hookedAt`을 기록하고 어종·크기 반환. 이른 요청 `too_early`, 늦은 요청 `too_late`, 두 번째는 `bad_action` |
| `resolve { success, perfect }` | 본인·미해결 확인. 실패는 언제든 pending을 지운다. 성공은 챈 뒤여야 하고(`not_hooked`) 챈 시각 + 2초 이후여야 한다(`too_early`). 성공이면 가방·도감 갱신 |
| `sell` | 가방 전체를 `price`로 값 매겨 `gold`, `total_earned` 증가, 가방 비움 |
| `buyRod { tier }` | 다음 단계·잔액 확인 후 차감 |

각 action은 한 트랜잭션, 세이브 행을 `for update`로 잠근다(두 탭 동시 요청 대비). 함수는 `_shared/db.ts`를 쓴다.

테이블 (마이그레이션 하나):

- `world_saves`: PK(`user_id`, `game_id`), `state jsonb`, `logic_version int`, `updated_at`. 낚시의 state = `{ gold, totalEarned, rodTier, areas, bag: [...], dex: {...} }`.
- 진행 중인 캐스트(`pending`)는 state 안에 둔다. 별도 테이블은 없다.
- `game_records`: PK(`user_id`, `game_id`, `key`), `value numeric`, `detail text`, `updated_at`. (6.4)

테이블 이름을 `fishing_*`가 아니라 `world_*`로 둔 건 플랫폼 규칙(게임별 분기 금지) 때문이다. 다음 지속형 게임이 같은 테이블을 쓴다.

RLS: `world_saves`는 본인 읽기만. `game_records`는 승인된 사용자 전체 읽기. 쓰기는 전부 Edge Function(서비스 역할)만.

**막는 것**: 골드·기록 직접 조작, 어종 지정, 가격 조작, 초당 수십 번 잡기. 다시 던져서 어종을 고르는 것은 한 번 볼 때마다 입질 대기 전체(1.5~6초)가 들고, 챈 뒤에야 어종이 보이므로 이득이 없다.
**못 막는 것**: 미니게임을 안 하고 `success: true`를 보내는 것. 경과 시간 제한 때문에 정상 플레이보다 빠르게 벌 수는 없다. 받아들인다.

**로직 버전**: `logic.version`을 올려도 세이브는 유지한다. 새 버전은 옛 state를 읽을 수 있어야 한다(없는 필드는 기본값). 가격표만 바뀌면 이미 가방에 있는 물고기는 판매 시점 가격표를 따른다.

**배포**: `data.ts`나 `logic.ts`를 바꾸면 `world` 함수를 다시 배포해야 한다(후알야 데이터와 같은 주의). `docs/deploy-checklist.md`와 CLAUDE.md에 추가한다.

### 6.4 프로필 기록 (플랫폼 공통 기능)

- `Manifest.records?: { key: string; label: string; unit?: string }[]` 추가.
- 낚시: `total_earned`(누적 수익, G), `biggest`(최대어, cm, detail에 어종 이름), `dex`(도감, detail에 "7/12").
- 서버가 `resolve`·`sell` 때 `logic.records()` 결과를 `game_records`에 upsert.
- 프로필에 **"기록" 탭**을 추가한다(요약 / 퍼즐 / 대전 / 기록 / 설정). 등록부에서 `records`가 있는 게임을 돌며 게임 이름 아래 항목을 나열한다. 플랫폼은 게임 id를 모른다.
- 조회는 RPC `user_records(p_handle)` (기존 `user_stats`·`duel_stats`와 같은 형태). 숨김 게임의 기록은 관리자에게만.

기존 `user_stats`는 건드리지 않는다.

## 7. 내가 정한 것 (사용자가 직접 고르지 않은 항목)

1. 총 자산 → **누적 수익**
2. 1차에 캐릭터 이동·맵 없음, 고정 화면
3. 잡은 물고기는 가방(20칸)에 넣고 상점에서 판매
4. 낚싯대 4단계·가격표, 어종 12종·가격대
5. Canvas 2D, 엔진 없음
6. 플랫폼에 `world` 종류를 새로 추가 (솔로·대전 계약에 끼워 넣지 않음)
7. 서버는 SQL 함수가 아니라 Edge Function (`logic.ts` 공유)
8. 테이블은 `world_*`·`game_records`로 범용 이름
9. 프로필에 "기록" 탭 신설, manifest `records`로 구동
10. 기존 리더보드 미편입, 배·먼바다 2차
11. 처음엔 `hidden: true`로 내고 관리자 확인 뒤 공개 (CLAUDE.md 절차)

독립적으로 PR을 나눌 수 있다.
1. 플랫폼: `world` 종류 + `world_*` 테이블 + Edge Function 뼈대 + 프로필 기록 탭 (테스트용 world 게임으로 검증)
2. 낚시 로직·데이터 + 서버 action
3. 낚시 화면(캔버스, 메뉴, 그래픽)
4. 숨김 배포 → 확인 → 공개
