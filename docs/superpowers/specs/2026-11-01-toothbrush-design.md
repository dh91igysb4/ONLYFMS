# 양치 시뮬레이터 (`toothbrush`) 설계

작성: 2026-11-01. 플랫폼 설계(`2026-10-31-onlyfms-platform-design.md`)를 따르고, 여기서는 이 게임과 그에 필요한 플랫폼 공통 변경만 다룬다. 독립 검토(1차)를 반영한 판이다.

변경 이력: v4(2026-11-02) — 위·아래 바깥을 다문 정면 '바깥' 하나로 합치고 '혀'(설태) 구역 추가, 칸당 총량 60 → 74로 난이도 상향(조준 봇 평균 8.37 → 7.40).

## 1. 목표와 범위

- 친구끼리 점수를 겨루는 1인 캐주얼 게임. 60초 동안 칫솔로 치아의 플라그를 문질러 지우고, 지운 비율로 점수를 받는다.
- **자유 플레이 전용.** 데일리·대회 없음 (`modes: { daily: false, contest: false, free: true }`).
- 판마다 플라그 배치가 무작위(층화 생성, §3.4). 리더보드는 이 게임만 **최고 점수** 기준 정렬.
- 점수는 기존 자유 플레이 방식대로 클라이언트가 계산해 `free_plays`에 저장한다(신뢰 모델 변경 없음). 출제 시드와 행동 로그를 함께 저장해 **재현**할 수 있게 한다(§5.3). 단, 로그 없이 `free_plays`에 직접 넣는 것도 여전히 가능하므로 로그는 검증 수단이 아니다. 리플레이·디버깅·밸런스 분석용이다.
- 처음에는 `hidden: true`로 머지하고 관리자 확인 뒤 공개한다.

범위 밖: 데일리·대회 모드, 리플레이 화면, 서버 재검증, 게임 화면 안의 "내 최고 기록"(리더보드 '최고' 열로 대신), 효과음.

## 2. 매니페스트

```

## 3. 로직 (`src/games/toothbrush/logic.ts`, 순수 함수)

모든 판정·채점 연산은 정수 덧셈·곱셈·나눗셈 후 `Math.floor`·비교뿐이다. `sqrt`·초월함수·부동소수 누적·`Math.random`·`ctx`를 쓰지 않는다. 난수는 `pickPuzzle`이 받은 `rng`만 쓴다. 시드와 행동 열이 같으면 어느 엔진에서든 결과가 같다.

### 3.1 시간
- 고정 틱 60Hz. 한 판은 `TOTAL_TICKS = 3600`(60초).
- 시간은 벽시계가 아니라 **입력 샘플 개수**로 센다. 샘플 1개 = 1틱.
- `ticks`가 3600이 되면 끝난다(`isFinished`). 모두 닦아도 일찍 끝나지 않는다(포기는 가능). 마지막 행동이 남은 틱보다 많은 샘플을 담고 있으면 앞에서부터 남은 틱만큼만 적용한다.

### 3.2 공간과 치아 마스크 (`src/games/toothbrush/mask.ts`)
- 구역 6개(`ZONE_LABELS`, 순서 고정, logic v4): 0 바깥(위·아래 바깥 면을 다문 채 함께), 1 위 안쪽 면, 2 위 씹는 면, 3 혀, 4 아래 안쪽 면, 5 아래 씹는 면. 시작 구역은 0. (v1~v3은 0 위 바깥, 3 아래 바깥이었다.)
- 구역마다 논리 좌표 `480 × 320`(정수). 플라그 격자는 `W × H = 48 × 32`칸, 1칸 = 10단위. 샘플 `(x, y)`의 칸은 `(⌊x/10⌋, ⌊y/10⌋)`. 칸 번호는 행 우선 `i = row × 48 + col`.
- **치아 형상은 구역마다 정수 기하 도형 목록**이다(`ZONE_SHAPES`, logic v2). 칸 `(c, r)`은 칸 중심 `(10c + 5, 10r + 5)`가 어떤 치아 도형 안에 있고, 구역의 `inside` 타원 모두의 안(입술 안쪽), `outside` 타원 모두의 밖(혀에 가린 곳)이면 **닦을 수 있는 칸**이다. 닦을 수 있는 칸은 치아 칸과 혀 구역의 혀 표면 칸을 함께 이르며, 마스크·생성·판정 규칙은 구역 종류와 상관없이 같다(코드의 `toothCells`·`isTooth` 이름은 그대로 두고 이 넓은 뜻으로 쓴다). 판정은 정수 곱셈·비교뿐이다(`sqrt`·초월함수 없음).
  - 치아 = 돌린 둥근 상자 `[종류, cx, cy, ax, ay, hw, hh, rg, re]`. 축 `(ax, ay)`는 길이가 약 `AXIS = 64`인 정수 벡터(잇몸 → 씹는 끝 방향). 오프셋 `(X, Y)`를 `u = ay·X − ax·Y`, `v = ax·X + ay·Y`로 바꾸고 `|u| ≤ hw·64`, `|v| ≤ hh·64`인 상자의 모서리를 반지름 `rg`(잇몸 쪽, `v < 0`)·`re`(끝 쪽)로 둥글린다(둥근 부분은 `qu² + qv² ≤ (r·64)²`). 축 길이가 정확히 64가 아니어도 같은 상자를 고르게 늘린 모양일 뿐이고, 그림이 같은 행렬의 역으로 그리므로 일치한다.
  - 타원 `[cx, cy, rx, ry]`: `X²·ry² + Y²·rx² ≤ rx²·ry²`.
  - 표의 정수는 부동소수로 배치를 계산해 한 번 정한 뒤 `mask.ts`에 상수로 적었다(생성 스크립트는 두지 않고 표를 직접 고친다. 모서리 반지름 유효성은 `mask.test.ts`가 검사한다). 화면 밖이라 칸이 없는 치아는 넣지 않는다. 치아 번호(`toothOf`)는 목록 순서.
- 구역별 모습(그림 `draw.ts`는 같은 도형을 캔버스 경로로 그린다):
  - 0 바깥: 입술 사이로 윗니와 아랫니가 맞물린(다문) 정면. 입 안쪽은 두 타원의 교집합(입꼬리가 화면 양옆 밖에 있는 넓은 렌즈 모양)이고 위아래를 입술과 피부가 감싼다. 위 잇몸선은 완만한 곡선이고 위 치아는 그 법선 방향으로 매달리며, 아래 치아는 같은 방식으로 만든 배치를 위아래로 뒤집어 아래 잇몸선에서 선다(옆으로 갈수록 두 잇몸선이 가까워지는 스마일 곡선). 앞니(중절치)가 가장 크고 측절치·송곳니·소구치·대구치 순으로 작아지며, 잇몸 쪽이 반원 아치라 치아 사이에 V자 치간이 생긴다. 아래 앞니는 위 앞니보다 좁다. 위 치아 10개를 먼저, 아래 치아 10개를 뒤에 두어 교합선에서 겹치는 칸은 위 치아 차지다(그림도 아랫니를 먼저 그리고 윗니가 그 끝을 덮는다). 폰 폭에서도 작지 않게 가장 작은 치아도 높이가 칫솔 원 지름(70단위) 이상이다.
  - 3 혀: 입을 벌리고 내민 혀를 위에서 본 모습(혀끝이 아래, 가운데 정중구 홈). 닦을 수 있는 도형은 혀 하나(`KIND_TONGUE`, 위가 평평한 상자 `[4, 240, 190, 0, 64, 130, 118, 0, 0]` ∩ `inside` 타원 `[240, 168, 124, 140]`)다. 벌린 입 구멍(`mouth`), 입술, 윗니·아랫니 끝(`decor`)은 그림 전용 장식이며 혀 아래에 그린다. 설태는 플라그와 같은 두께 모델이고 그림만 희끄무레한 크림색과 알갱이 얼룩으로 그린다(치아 플라그의 노란색과 구분).
  - 1 위 안쪽 / 4 아래 안쪽: 안에서 본 같은 치열. 가까운 어금니가 크고 먼 앞니가 작다. 1은 입천장(주름·가운데 솔기)이 치아 위를 채우고 아래에 혀끝(`tongue`, 그림 전용)이 보이며, 4는 아래쪽 앞에 혀가 보인다(혀 타원은 `outside`). 혀 쪽 면 표시(앞니 융기, 어금니 교두).
  - 2 위 씹는 면 / 5 아래 씹는 면: 위(아래)에서 본 U자 치열(타원 호를 따라 배치, 2는 앞니가 위, 5는 앞니가 아래). 앞니는 가늘고 어금니로 갈수록 크다(씹는 면 홈). U 안쪽에 2는 입천장, 5는 혀(`tongue`, 그림 전용). 치열 타원 `arch`도 그림 전용이다.
  - 그림 전용 도형(`arch`, `tongue`, `mouth`, `decor`)도 `ZONE_SHAPES`에 두어 그림의 단일 출처를 유지한다. 판정은 `teeth`·`inside`·`outside`만 쓴다.
- 닦을 수 있는 칸 수: 구역 0~5 = `886, 440, 484, 492, 442, 466`(합 3,210, 구역마다 400~900). 도형 개수 20/8/12/1/8/14(치아는 화면 밖인 것을 빼고, 3은 혀 하나). 테스트로 고정한다. (v3까지는 `504, 440, 484, 458, 442, 466`.)
- 마스크는 모듈 로드 시 한 번 계산한 상수다. 바꾸면 `logic.version`을 올린다.

### 3.3 행동
- `{ type: 'b', s: number[] }` — 문지르기. `s`는 `[x0, y0, x1, y1, …]`, 샘플 하나가 1틱. 접촉 없는 틱은 `-1, -1`. 배열 길이는 짝수, 샘플 수는 1~30. 각 값은 정수이고, 샘플은 `0 ≤ x < 480`, `0 ≤ y < 320`이거나 정확히 `(-1, -1)`. 어긋나면 `{ error }`(상태 불변).
- `{ type: 'z', zone: k }` — 구역 전환. 정수 `0 ≤ k < 6`, 현재 구역과 달라야 하고, **시계가 시작된 뒤(`ticks > 0`)에만** 허용된다. 틱을 쓰지 않는다. 전환하면 `cooldown = SWITCH_TICKS (30)`, `prev = null`.
- `{ type: 'give_up' }` — 플랫폼 공통. `ticks = 3600`으로 만들어 끝낸다.
- 끝난 뒤의 모든 행동은 `{ error }`.

### 3.4 플라그 배치 (`pickPuzzle`, 층화 생성)
퍼즐은 구역별 칸 두께 배열 6개(각 1536칸, 정수 0~`MAX_THICK = 255`, 치아 아닌 칸은 항상 0)다. 구역마다 순서대로:

1. **기본층**: 모든 치아 칸 = `BASE (20)`. 시작값일 뿐이며, 3단계 총량 맞추기가 이를 깎아 없앨 수 있다(현재 상수에서는 덩어리 밖 치아 칸 상당수가 0이 된다). 그래서 최종 플라그는 덩어리에 모인다.
2. **덩어리**: `BLOBS (6)`번 반복. 중심 = 치아 칸 목록(행 우선 고정 순서)에서 `⌊rng() × n⌋`번째, 반지름 `r = 3 + ⌊rng() × 4⌋`(3~6). 중심에서 `dx² + dy² ≤ r²`인 치아 칸(격자 밖·치아 아닌 칸 제외)에 `BLOB_ADD (140)`를 더하고 `MAX_THICK`에서 자른다. rng 호출 순서: 덩어리마다 중심 → 반지름.
3. **총량 맞추기**: 구역 총량을 정확히 `ZONE_TOTAL[z]`로 맞춘다. 후보는 그 구역의 **모든 치아 칸**(행 우선 고정 순서). 모자라면 후보를 처음부터 순환하며 `MAX_THICK` 미만인 칸에 1씩 더하고, 넘치면 순환하며 0 초과인 칸에서 1씩 뺀다. 한 칸에 몇 번이든 들를 수 있다.
   - 종료 보장: `0 ≤ ZONE_TOTAL[z] ≤ 치아 칸 수 × MAX_THICK`이면 매 순환마다 최소 1은 움직이므로 반드시 끝난다(상한은 칸 수 × 255, 가장 작은 구역 1에서 112,200). 이 부등식을 상수에 대한 테스트로 확인한다. 루프는 칸 하나씩이 아니라 "한 바퀴에 일괄"로 구현해도 결과가 같아야 한다.
- 결과: 판마다 덩어리 위치는 달라도 **구역별 총량이 항상 같다** → 맵 운이 줄어든다. 플라그가 덩어리에 몰려 있으므로 "두꺼운 데를 찾아가 그 자리를 문지르기"가 실력 요소다. 줄 단위로 고르게 훑으면 빈 칸에서 시간을 버린다.
- `puzzleKey`: 6개 배열을 이어 붙인 값의 FNV-1a 32비트 해시(16진 8자). 곱셈은 `Math.imul`, 결과는 `>>> 0`.

### 3.5 브러싱 모델 (틱마다)
틱마다 샘플 `p`에 대해 순서대로:

1. `p = (-1, -1)`(접촉 없음): `prev = null`. 끝.
2. `d² = (p.x − prev.x)² + (p.y − prev.y)²`. `prev`가 null이면 `d² = 0`. 그 뒤 `prev = p`(전환 대기 중에도 갱신).
3. `cooldown > 0`이면 `cooldown −= 1`. 닦지 않고 잇몸도 늘지 않는다. 끝.
4. 속도 구간(단위²/틱²):

   | 구간 | 조건 | 속도(단위/s) | 칸당 감소 `dec` | 잇몸 |
   |---|---|---|---|---|
   | 느림 | `d² < 4` | < 120 | 1 | — |
   | 최적 | `4 ≤ d² < 900` | 120 ~ 1,800 | 4 | — |
   | 빠름 | `d² ≥ 900` | ≥ 1,800 | 1 | `gumTicks += 1` |

   (v1의 빠름 경계 144(초당 720)는 폰에서 평범하게 문질러도 22초 중 13초가 빠름으로 잡혀 v2에서 900(틱당 30단위)으로 올렸다.)

5. 칫솔 중심 칸 `(cx, cy)`에서 `dx² + dy² ≤ R² (R = 3)`인 칸(최대 29칸, 격자 밖은 건너뜀)마다 `t = min(dec, 두께)`만큼 빼고 `removed += t`. 두께는 0 아래로 내려가지 않는다.

틱 증가(`ticks += 1`)는 샘플마다 1~5와 무관하게 일어난다.

### 3.6 상태·점수
- 상태: `{ zones: number[][] (6 × 1536), zone, ticks, cooldown, prev: [x, y] | null, gumTicks, switches, removed }`. `apply`는 바뀌는 구역 배열만 복사해 바꾸고 입력 상태를 변경하지 않는다.
- `TOTAL = Σ ZONE_TOTAL`. 점수(정수 0.01점 단위로 계산, v3부터. v1·v2는 0.1점 단위였다):
  - `hundredths = ⌊(1000 × removed + ⌊TOTAL / 2⌋) / TOTAL⌋ − 10 × ⌊gumTicks / 60⌋`
  - `score = clamp(hundredths, 0, 1000) / 100`
  - 저장은 `free_plays.score numeric(4,2)`(마이그레이션 `20261102052719_free_score_two_decimals`), 리더보드 평균·최고도 소수 둘째 자리. 화면은 이 게임(`freeStats: 'score'`)만 둘째 자리로 표시하고, 다른 자유 플레이 게임의 평균은 지금처럼 첫째 자리로 표시한다.
  - 즉 빠르게 문지른 1초마다 0.1점 감점이다. 끝나지 않았을 때도 같은 식("지금 포기하면 받을 점수").
- `actionCount = switches`(구역 전환 횟수). 자유 플레이 정렬에는 쓰이지 않는다.
- `publicState`: `{ zones, zone, ticksLeft, cooldown, gumTicks, started: ticks > 0, cleanByZone: number[] }`. `cleanByZone[z] = ⌊100 × (ZONE_TOTAL[z] − 남은 총량) / ZONE_TOTAL[z]⌋`(내림이라 플라그가 남아 있으면 100이 되지 않는다).
- `reveal`: `null`.
- 플랫폼의 `solved`(`score > 0`)는 그대로 둔다. 이 게임에서는 거의 항상 참이라 정답·정답률 열은 의미가 약하지만, 정렬은 최고 점수라 문제 삼지 않는다.

### 3.7 상수와 난이도 목표
현재값(logic v4): `BASE = 20`, `BLOB_ADD = 140`, `BLOBS = 6`, 반지름 3~6, `MAX_THICK = 255`, `R = 3`, 속도 경계 `4 / 900`, 감소량 `1 / 4 / 1`, 감점 0.1점/초, `SWITCH_TICKS = 30`, `ZONE_TOTAL = [65564, 32560, 35816, 36408, 32708, 34484]`(= 닦을 수 있는 칸 수 × 74, 합 237,540). v2·v3은 칸 수 × 60(`[30240, 26400, 29040, 27480, 26520, 27960]`, 합 167,640). v1은 `ZONE_TOTAL = [36380, 36380, 27285, 36380, 36380, 27285]`(합 200,090), 빠름 경계 144였다.

- **용량비 목표**: 칫솔이 매 틱 29칸 모두 최적 감소를 낼 때의 최대 제거량은 `29 × 4 × (3600 − 5 × 30) = 400,200`이다. 허용 범위는 1.5~2.4다. v4는 400,200 / 237,540 ≈ 1.68이다(v2·v3은 ≈ 2.39). 입 모양 치아는 치아 사이·둘레가 비어 칫솔 원 29칸 중 평균 20~24칸만 치아에 닿고, 씹는 면은 U자라 이동이 길어서 같은 용량비 2.0에서는 조준 봇이 평균 7.7점에 그쳤다. 그래서 총량을 칸 수에 비례로 두고 용량비를 상한 가까이 올렸다(생성 상수는 v1 그대로, `BLOBS`·반지름·`BASE`를 바꿔도 조준 봇이 거의 안 변했다). 400,200은 칫솔 29칸이 매 틱 모두 플라그에 닿는 이론상 상한이다. 실제로는 칫솔 가장자리가 이미 깨끗한 칸에 걸리고, 동선이 겹치고, 최적 속도로 계속 움직여야 해서 한 곳에 오래 머물 수 없다. 그래서 상한이 총량의 2배여도 다 지우기 어렵다. v2·v3에서는 조준 봇(사람 상한 근사)이 평균 약 84%를 지웠고, 사람 최고 기록(9.46)이 조준 봇보다 높아 v4에서 난이도를 올렸다: 칸당 총량을 60 → 74로 올려 조준 봇이 평균 약 74%를 지운다(§7). 생성 상수는 그대로다.
- 이 수치는 §7 밸런스 테스트가 통과하도록 조정한 값이다. 공개 뒤 조정할 때마다 `logic.version`을 올린다.

## 4. 화면 (`src/games/toothbrush/Game.tsx`)

- 레이아웃(모바일 우선): 남은 시간 막대 → 잇몸 게이지 → 3:2 캔버스(컨테이너 폭) → 구역 버튼 6개(2×3, 각 청결도 % 표시). 구역 전환은 버튼으로만 한다(스와이프는 문지르기와 충돌). 시작 전(`started = false`)에는 구역 버튼이 비활성이다(로직도 거부). 그래서 다른 구역 지도를 미리 볼 수 없다.
- 입력: Pointer Events로 마우스·터치를 통합하고, 캔버스에 `touch-action: none`을 건다. 접촉 = 포인터 누름. 화면 좌표 → 논리 `480 × 320` 정수, 영역 밖은 가장자리로 고정.
- 샘플링: rAF마다 `performance.now()` 누산기로 지난 시간만큼 60Hz 샘플 `n`개를 만든다. 샘플 위치는 직전에 내보낸 위치와 현재 포인터 위치 사이를 정수 선형 보간한다(`x_i = x0 + ⌊(x1 − x0) × i / n⌋`, i = 1..n). 프레임률(30/60/120Hz)과 무관하게 같은 손동작이 같은 `d²`를 내게 하려는 것이다. 접촉이 없으면 `(-1, -1)`.
- 프레임 간격이 250ms를 넘으면(탭 전환, 끊김) 그 공백은 버리고 `(-1, -1)` 샘플 하나를 넣는다(`prev`를 끊어 순간이동이 빠름 구간으로 판정되지 않게). **탭을 숨기면 게임이 멈추는 것은 의도된 동작이다.**
- 모은 샘플은 50ms마다 `onAction({ type: 'b', s })`로 보내고, 30샘플을 넘으면 여러 행동으로 나눈다.
- **시계는 캔버스를 처음 누른 순간부터 간다.** 그 전에는 샘플을 만들지 않는다.
- 렌더링: §3.2의 도형으로 입술·잇몸·입천장·혀와 치아를 그리고, 플라그는 칸마다 두께에 비례한 불투명도를 48×32 이미지에 찍어 부드럽게 확대한 뒤 치아 합집합으로 잘라 덮는다(딱딱한 칸 사각형이 보이지 않게). 칫솔 커서는 포인터를 즉시 따라가고, 닦임 반영은 최대 50ms 늦다. 빠름 구간이면 잇몸 게이지가 붉게 깜빡이고, 전환 대기 중에는 캔버스를 흐리게 표시한다.
- 끝나면: 점수, 구역별 청결도, 잇몸 손상 초. 그 아래에 플랫폼의 "한 판 더".
- 색: 캔버스 바깥 UI는 `theme.css`·팔레트 토큰만 쓴다. 캔버스 안의 치아·플라그·잇몸 색은 예외이며 `CLAUDE.md` 금지 사항의 예외 목록에 추가한다.

### 5.3 행동 로그 저장 (모든 자유 플레이 게임)
**LocalRunner 상태 관리 수정** (로그와 점수가 어긋나지 않게 하는 선행 조건):
- 지금 `onAction`은 렌더 클로저의 `state`에 적용한다. 한 렌더 안에서 행동이 두 번 오면(샘플 분할, 같은 틱의 구역 클릭) 뒤 행동이 앞 행동을 덮어쓴다.

**테이블 `free_play_logs`** (새 마이그레이션):
```
client_id  uuid primary key references free_plays(client_id) on delete cascade
user_id    uuid not null references auth.users(id) on delete cascade
seed       text not null  check (seed ~ '^[0-9a-f]{32}$')
actions    jsonb not null check (jsonb_typeof(actions) = 'array')
created_at timestamptz not null default now()
check (octet_length(actions::text) <= 262144)   -- 256KB. jsonb::text는 공백이 붙어 원문보다 약 25% 크다

- RLS·권한(0002 패턴):
  - `security definer` 도우미 `public._owns_free_play(p_client uuid) returns boolean`: `free_plays`에서 `client_id = p_client and user_id = auth.uid()`인 행이 있는지 본다. 호출자 RLS를 거치지 않으므로, 숨김 게임이 되어도 본인 기록 확인이 막히지 않는다. 도우미는 0002 패턴대로 `revoke execute … from public, anon, authenticated` 후 `grant execute … to authenticated`(정책이 invoker 권한으로 부르므로).

  - 테이블 권한: `revoke all … from public, anon, authenticated` 후 `grant select … to authenticated`, `grant insert (client_id, user_id, seed, actions) … to authenticated`(0002의 `free_plays`처럼 열 단위).

  - 같은 `client_id`가 아직 점수 대기열(`freeQueue`)에 있으면 건너뛴다(점수 행이 먼저 저장돼야 함).
