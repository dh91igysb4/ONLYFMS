# 펨타듀 낚시 후반 경제 설계 (연구·전시·포션·전시관·완료 후 목표)

외부 경제 모델 제안(개정3 `2026-11-27-r3-integrated`, 기준 커밋 `d5838bd`)을 이 레포에 맞춘 설계다. 2026-11-28에 **4.5개월 기준(r4)** 으로 수치를 다시 맞췄다(§6.4). 제안 패키지는 레포 밖에 있고(관측 원자료에 실제 유저 잔액이 들어 있어 커밋하지 않는다), 구현에 필요한 규칙·수치는 이 문서에 옮긴다. 수치는 모형 결과이며 실제 구매율·안정 효과는 운영에서 확인한다.

## 1. 목표

장비·지역을 다 연 뒤에도 (1) 전설·신화를 다시 낚을 이유, (2) 여러 지역을 다시 갈 이유, (3) 골드를 반복해서 쓰고 큰 목표를 위해 모을 이유를 만든다. 기본 낚시는 계속 무료이고, 초반 진행 속도(하루 1시간 장비·해금 약 24일, `fishing/gold.test.ts`)는 21~31일 안에 둔다. 모든 새 지출은 선택이다.

**기준 기간(r4, 사용자 결정 2026-11-28)**: 하루 1시간 하는 사람이 약 4.5개월(135일) 안에 13종 전시를 끝내고 완료 후 목표(테마·시설)를 모두 살 수 있게 한다. 그 뒤에는 새 콘텐츠를 더하지 않는 한 골드가 다시 쌓인다(§2.6).

## 2. 기능과 수치 (r4)

### 2.1 단계

| 단계 | 해금 판정 | 기능 |
|---|---|---|
| A | 처음 ~ 첫 신화 영구 전시 전 | 무료 기본 낚시, 장비·지역, 어분·미끼·연구·기증·전시 |
| B | 첫 신화 영구 전시 소유 | 지역 재료, 기본 10분 1병 포션, 전시관 확장 5단계 |
| C | 정해진 13종(전설 10·신화 3) 영구 전시 모두 소유 | 20분 3병 포션 제작법, 6테마 18부품·3시설 |

A→B는 신화 최초 포획이 아니라 전시 소유, B→C는 도감 발견 수가 아니라 13종 영구 전시 소유로 판정한다.

### 2.2 미끼·연구·전시 (P1·P2)

| 기능 | 골드 | 재료·소모 | 해금 |
|---|---|---|---|
| 어분 | 0 | 일반 물고기 1 → 어분 1 | 처음부터 |
| 집어 미끼 | 50 | 어분 1 → 미끼 1. 다음 유효 투척 1회 일반 rare 가중치 ×1.2 | 처음부터 |
| 연구 해금 | 50,000 (계정당 1번) | — | 전설 1종 발견 |
| 전설 미끼 | 600 | 어분 1 → 미끼 1 | 연구 해금 + 그 등급 발견 |
| 신화 미끼 | 1,200 | 어분 2 → 미끼 1 | 연구 해금 + 그 등급 발견 |
| 전설 전시 | **100,000** (r3 200,000) | 같은 어종 새 재포획 2마리 기증 | 최초 발견 기록 |
| 신화 전시 | **250,000** (r3 500,000) | 같은 어종 새 재포획 2마리 기증 | 최초 발견 기록 |

- 연구 낚시: 발견한 전설·신화를 골라 전용 미끼 1개로 던진다. 계절·시간·날씨만 완화하고 지역·자리·낚싯대·힘·물때는 그대로다. 대상 입질 전설 1.5%(호기심 찌 2.25%)·신화 0.75%(1.125%)(2026-11-28 v28, 사용자 결정: 원래 3%·1%를 절반으로. 보장까지 평균 투척 수가 전설 26.1 → 35.4회, 신화 63.4 → 70.5회로 늘어 미끼 골드가 그만큼 더 든다. 135일 진행 모형은 다시 재지 않았다). 대상별 유효 투척 50회(전설)·100회(신화)째는 입질 보장(포획 보장 아님). 잡으면 0, 놓치면 유지. 거절된 투척은 미끼를 쓰지 않는다. 연구 투척에서는 다른 전설·신화의 최초 발견이 나오지 않는다.
- 연구 진행도 3 = 최초 발견 기록 1 + 새 재포획 2마리 기증. 연구 보장(50/100)과 다른 수치다.
- 판매가: 일반·legacy·first는 지금 가격, recatch는 `round(판매가 × 0.5)`. 기증한 개체는 팔거나 분해할 수 없다.
- 13종 전시료 합계 175만 G(r3 350만 G).

### 2.3 지역 가격 보정 (P1, 구현됨)

섬·갯벌·산정 호수의 일반 어획 50종 기본가만 올린다(섬 ×1.30, 갯벌 ×1.08 후 10G 반올림, 산정 일반 ×4/3·고급 ×1.30 후 10G 반올림·희귀 1,500G). 전설·신화 13종, 초반 5지역, 늪지·난파선, 장비·해금비는 그대로다. 가방에 있는 일반 물고기도 새 가격으로 팔린다(과거 판매 차액은 없다). 결과: 하루 1시간 장비·해금 25.1 → 24.3일, 산정 얼음 구멍 시간당 수입 ≈ 동굴 용암 × 1.6(난파선 심해 이하).

## 3. 기존 코드와 맞춘 점 (2026-11-27 `main` 대조)

- 제안의 소스 스냅샷 32개 파일 중 31개가 `main`과 같다(다른 하나는 `types.ts`의 게임 탭 `topic`, 무관). 낚시 `logic.version` 25.
- `Fish`는 `species/sizeCm/perfect/locked`뿐이고 `migrate`가 이 네 칸으로 다시 만든다 → 새 칸을 넣으려면 `migrate`부터 고친다(§4).
- `resolve`는 `success`·`perfect`를 브라우저가 보내고 서버는 대기 상태와 `MIN_FIGHT_MS`만 본다. 연구로 비싼 재포획을 열기 전에 판정 경계를 다시 설계해야 한다(§6 결정 필요).
- `world` 핸들러는 세이브 → 지갑 순서로 잠근 한 트랜잭션이지만, 같은 HTTP 요청이 두 번 오면 두 번 처리한다(장부 `ref`가 요청마다 무작위). 화면은 재시도하지 않아서, 응답만 잃으면 사용자가 다시 누를 때 두 번 반영된다.
- 물고기를 다루는 행동: `resolve`(넣기)·`sell`·`lock`·`discard`·`discardMany`·`store`·`takeOut`. 지금은 가방 위치 + 어종·크기로 가리킨다.
- 전시관 위치는 제안이 정하지 않았다 → 마을회관 2층으로 정했다(§6.2).

## 4. P0: 데이터·거래 안전장치 (2026-11-27 배포 완료, v26)

새 기능 없이 바탕만 깐다. 화면에 보이는 변화는 없다.

### 4.1 `world` 요청 중복 방지 (플랫폼, 모든 지속형 게임)

- 화면은 `act` 요청마다 `action_id`(UUID)를 만들어 본문 최상위에 보낸다. 네트워크 오류(응답을 못 받음)·5xx면 같은 `action_id`로 최대 2번 다시 보낸다.
- 핸들러는 세이브 행을 잠근 뒤 `world_actions`(사용자·게임·`action_id`, `payload` 해시, 응답 본문)를 본다.
  - 같은 ID·같은 payload: 저장한 응답을 그대로 돌려준다(세이브·지갑·기록을 다시 쓰지 않는다).
  - 같은 ID·다른 payload: 409 `action_id_reused`, 아무것도 바꾸지 않는다.
  - 처음 보는 ID: 지금처럼 처리하고, 200 응답이면 같은 트랜잭션에서 `world_actions`에 쓴다. 오류 응답은 저장하지 않는다(바뀐 것이 없으니 다시 처리해도 같다).
- 골드 장부 `ref`는 `action_id`(없으면 지금처럼 무작위). 장부 unique `(user, reason, ref)`가 두 번째 안전장치다.
- `action_id`는 선택이다(배포 중 옛 화면). 형식은 UUID만 받는다(아니면 400).
- `world_actions`는 클라이언트가 읽지 못한다(RLS 켜고 정책 없음). 하루 지난 행은 그 사용자의 다음 기록 때 지운다.

### 4.2 낚시 물고기 고유 ID·출처 (`logic.version` 26)

- `Fish`에 `id`(세이브 안에서 유일한 양의 정수)와 `origin`(`legacy` | `first` | `normal` | `recatch`)을 더한다. `State.nextFishId`가 다음 번호다.
- 옛 세이브(v25 이하): 가방 → 냉장고 순서로 1부터 번호를 붙이고 `origin: 'legacy'`. `nextFishId`는 그다음. 잠금·크기·퍼펙트·순서·개수는 그대로다(v25까지의 기존 정리 규칙만 적용).
- v26 이상 세이브를 다시 읽을 때: `id`·`origin`을 보존한다. `id`가 없거나 겹치거나 `nextFishId` 이상이면 그 개체만 새 번호(`origin`은 있으면 유지, 없으면 `legacy`).
- `resolve`: 전설·신화는 `first`(지금은 한 번만 잡힌다), 나머지는 `normal`. `recatch`는 P1 연구 낚시에서만 만든다.
- `lock`·`discard`·`discardMany`·`store`·`takeOut`은 `id`를 받으면 그 위치의 개체 `id`와 같은지도 본다(다르면 지금과 같은 `bag_changed`/`fridge_changed`). `id`가 없으면 지금처럼 동작한다(옛 화면).
- 판매가·확률·진행 속도는 바뀌지 않는다.

### 4.3 P0 인수 조건

- 같은 `action_id`를 두 번(차례로) 보내면 골드·세이브 변화는 1번이고 두 응답이 같다(제안 A01의 순차 부분. 동시 요청은 세이브 행 잠금으로 줄을 선다).
- 같은 `action_id`에 다른 payload는 409이고 변화 0.
- v25 세이브 fixture를 v26으로 읽으면 물고기 수·순서·크기·퍼펙트·잠금, 도감·전설·버프·장비·지역·옷·섬·집이 그대로이고, 모든 물고기에 서로 다른 `id`와 `origin: 'legacy'`가 붙는다. 두 번 migrate해도 같다.
- 스테일 화면이 보낸 `id`가 다르면 거절되고 변화 0.

각 단계는 `logic.version`을 올리고 `migrate` 테스트를 더하고 `world`를 다시 배포한다. 새 기능은 기능 플래그로 끌 수 있게 하고, 꺼도 기존 낚시·자산은 그대로다. P1을 배포하면 플래그와 무관하게 지역 가격 보정은 바로 적용된다.

## 6. 결정

1. **판정 경계 (2026-11-27 결정: 서버 싸움 시간 검사)**: 성공 여부는 계속 브라우저가 알리되, 서버가 저장한 챔질 시각(`hookedAt`) 기준으로 `resolve` 시각이 어종·장비별 최소~최대 싸움 시간 안에 있어야 성공으로 인정한다. 밖이면 성공을 거절한다(놓친 것으로 처리할지 오류로 돌려줄지는 P1 설계에서). 범위는 `minigame.ts` 봇 시뮬레이션으로 정하고, 정상 플레이가 걸리지 않는지 시험으로 확인한다. 성공률 이상치 관측은 하지 않는다. P1에서 연구 낚시보다 먼저 넣는다.
2. **전시관 위치 (2026-11-27 결정: 마을회관 2층)**: 회관에 계단을 두고 2층 맵·그림(`scripts/hall-art/`, `maps/hall.ts` 규칙)을 새로 만든다. 전시 칸은 `fixtures`로 두고, 확장 5단계(P4)는 같은 2층 공간을 넓히거나 꾸미는 방식으로 한다.
3. **포션 활동 시간(P3 전, 미정)**: 서버가 인정하는 "활동 중" 구간(제안 G02). 탭 방치·오프라인에서 효과가 줄거나 무한히 남지 않게.
4. **기준 기간 4.5개월 (2026-11-28 결정, r4)**: 개정3은 365일 관찰 창에서 완료 후 목표를 1년에 걸쳐 사게 했다. 하루 1시간 기준 약 135일 안에 13종과 목표를 다 끝내도록 전시료 ×0.5, 확장 ×0.3, 완료 후 목표 골드 ×0.2·재료 ×0.5로 낮췄다. 같은 모형(개정3 `postcollection` 모형 사본, 경로마다 골드·재료 보존 검사)으로 576경로를 다시 계산했다. 대가: 목표를 다 산 뒤 잔액은 개정3보다 훨씬 크다.

## 7. 배포

P0는 DB 마이그레이션(`world_actions`) → `world` 함수 → Vercel 순서다. 새 함수는 `action_id` 없이도 동작하므로 옛 화면과 함께 돌아간다. 낚시 v26은 `world` 배포와 함께 들어가며 v25 아래로 되돌리지 않는다(`version_newer` 보호).
